## Mission

OxidHome is an open home-automation platform that combines a Rust core with WebAssembly plugins. The goal is a hub that is:

- **Safe to expose** to a home network (memory-safe core, sandboxed plugins, capability-scoped permissions)
- **Fast enough** to react in real time on modest hardware
- **Flexible enough** to support the long tail of devices, protocols, and integrations
- **Honest about its limits** — when WASM isn't the right answer, the architecture provides a well-marked escape hatch rather than pretending

The design is informed by what works (and doesn't) in Home Assistant, Scrypted, Frigate, Matter, and similar systems.

## Core technical choices

### Rust for the core

The hub sits in a privileged spot on the network. Memory safety without a GC, predictable performance, and a runtime small enough to live alongside devices on the same hardware are non-negotiable. Rust delivers all three.

### WebAssembly (Component Model) for plugins

Plugins are `.wasm` components — not raw `.wasm` modules. The Component Model is the foundation, not an optimization:

- Rich types across the host/plugin boundary (no manual serialization boilerplate)
- Language-agnostic plugin authoring (Rust first, but Go, JS, Python, C# all viable)
- Capability-based imports — plugins can only do what the host imports give them
- Standard interfaces (WASI 0.2) for HTTP, sockets, clocks, etc.

### Wasmtime as the runtime

Best Component Model support, async host functions, mature embedding API, well-maintained by the same group that chairs the WASM spec work.

### WIT as the API contract

The `oxidhome.wit` file is the *real product* in a sense. Once plugins exist in the wild against version 0.1 of the WIT, breaking changes get expensive. The WIT deserves real care on the first cut.

Compatibility is proven from the component binary, not taken from the manifest. Every component carries the WIT types of what it imports and exports, under their full names (`oxidhome:plugin/host-devices@0.1.0`). Before compiling a plugin, the loader (`oxidhome_core::runtime::contract`) decodes those types and compares them with the host's own `oxidhome:plugin` package, which `build.rs` bakes in from `wit/`. The package version must be the host's own or an older one on the same compatibility line (same `0.x` minor, or same major after 1.0), and every function the component imports or exports from the package, plus every export the `plugin` world requires, must match the host's signature structurally. A component may import a subset of an interface. A component that fails the check is refused with an error naming the offending item. So is a component that carries no `oxidhome:plugin` types at all, or whose types can't be decoded: there is no warn-only mode. The manifest's `sdk_version` check still runs, but only as a secondary signal of the author's intent.

A contract version is immutable once it has a baseline in `crates/oxidhome-wit/baselines/`. The `contract_baseline` test fails when `wit/` drifts from the current version's baseline, and it semver-checks compatible bumps against the previous version. CONTRIBUTING.md describes the bump-and-bless workflow.

## The plugin model

### Plugin vs. plugin instance

- A **plugin** is a `.wasm` component package — the code (e.g. "onvif-camera", "zigbee2mqtt-bridge")
- A **plugin instadsance** is a configured, running copy of that plugin (one per camera, one per Zigbee bridge, etc.)

A user installs the "ONVIF camera" plugin once. They configure three cameras through the UI. The host spins up three component instances of that plugin, each with its own config, capabilities, and lifecycle. Crash isolation, per-instance supervision, and independent updates fall out naturally.

Plugin manifests declare whether the plugin is **singleton** (Zigbee coordinator owns the radio — only one instance makes sense) or **multi-instance** (cameras, MQTT brokers).

### The three plugin worlds

The WIT defines multiple worlds, each adding capabilities on top of the previous:

| World                               | Purpose                                                       | Examples                                                             |
|-------------------------------------|---------------------------------------------------------------|----------------------------------------------------------------------|
| `plugin`                            | Standard device integrations, automations, logic. No raw I/O. | Switch drivers, sensor adapters, scene controllers, automation rules |
| `streaming-plugin`                  | Adds WASI sockets and HTTP for long-lived I/O.                | Cameras, MQTT bridges, voice assistants, network discovery           |
| `ai-plugin` / `streaming-ai-plugin` | Adds the `inference` import for using host-managed ML models. | Person detection, audio classification, anomaly detection            |

Importing a WASI interface does **not** grant access to it. Capabilities are gated by the plugin manifest the user approves at install time. The host enforces network allowlists, filesystem scopes, model access, etc. per instance.

The world an instance runs is the one its manifest's `[plugin] world` names, and it decides what the instance's linker gets. `plugin` and `ai-plugin` instances get only the WASI that libstd needs (`wasi:cli`, `wasi:clocks`, `wasi:io`, `wasi:random`, `wasi:filesystem` with no preopens); a component of theirs that imports `wasi:sockets` or `wasi:http` fails to load. Streaming instances also get `wasi:sockets` and outgoing `wasi:http` (Phase 8; see [Network access](#network-access-phase-8)). `host-media` is linked for them too, but answers `unavailable` until media pipelines land.

## The device model

### Capabilities, not device types

Device archetypes are not enumerated as types. Instead, devices declare a list of **capabilities** — small, reusable units of functionality:

- A bulb = `[switch, dimmer, color-light]`
- A doorbell = `[button, video-stream, audio-stream, motion-detector]`
- A thermostat = `[temperature-sensor, target-temperature, mode-selector]`
- A robot vacuum = `[command, battery-sensor, status-reporter]`

This matches what Home Assistant, Matter, HomeKit, and SmartThings all converged on. Consumers (UIs, automations, voice integrations) ask "does this device support brightness?" not "is this device a SmartBulb_v3?"

The capability variant includes an `extension(extension-spec)` arm so plugin authors can add new capability types without waiting for the core spec to catch up. An extension is identified by a reverse-DNS `namespace`, a `name`, and a major schema `version` (`com.acme` / `window-shade` / `1`), never by a free-form string: the host validates the identity at `register-device` (`oxidhome_manifest::ExtensionId`, namespaces starting with `oxidhome` are reserved), and the manifest's `declares_devices` and the state projection both spell it as the capability key `extension(com.acme/window-shade@1)`. A different schema version is a different capability, so a grant for `@1` does not authorize `@2`. Consumers that don't recognize an extension identity simply ignore the capability (forward compatibility).

### Standard capabilities

The WIT defines:

- `switchable` — discrete on/off
- `dimmable` — continuous 0.0–1.0 level (brightness, fan speed, blind position)
- `color` — HSV + optional color temperature
- `measurement` — numeric reading with a typed `unit`
- `button-event` — stateless press/release/rotation events
- `video-stream` / `audio-stream` — references to media streams
- `lock` — `lock-state` (`locked`, `unlocked`, `locking`, `unlocking`, `jammed`)
- `opener` — garage doors, gates, doors, windows: `opener-spec` (kind, whether it reports a position) and `opener-status` (`open` / `closed` / `opening` / `closing` / `stopped`, optional 0.0–1.0 position)
- `alarm-panel` — `alarm-panel-spec` (1–8 armed modes, whether a code is required) and `alarm-state` (`disarmed`, `armed-home` / `away` / `night` / `vacation`, `arming`, `pending`, `triggered`)
- `siren` — on/off
- `extension(extension-spec)` — namespaced, versioned plugin-defined capabilities

Sensor units are the closed WIT variant `unit` (`celsius`, `percent`, `kilowatt-hour`, `ppm`, ...). The named cases are the contract: consumers may convert and aggregate by them, and each case's kebab-case name is its code in the state projection (`unit = "celsius"`). `other(label)` is a display-only fallback for quantities the set doesn't cover; the projection keeps it apart (`unit = "other"`, `unit_label = <label>`), consumers must not interpret the label, and the host refuses a label that spells a named code. `register-device` also refuses a non-finite or inverted `sensor-spec` range and an initial reading whose unit differs from its spec's, and every sensor `state-changed` event or `ok-with-state` reply must carry `unit` (and `unit_label`, for `other`) exactly as the spec declares them, so no reading reaches the projection without its unit (`oxidhome_sdk::sensor_fields` builds that bag). An `update-device` that changes a sensor's unit flips its projected reading `Stale`. Adding a unit is a WIT contract change.

This is intentionally a small starting set. Expect it to grow as real devices are integrated.

### Device categories (H6 slice 2)

The host derives a **category** for every device from its capabilities; plugins don't declare one. In precedence order: `alarm` (`alarm-panel`, `siren`), `lock`, `opener`, `camera` (`video-stream`), `light` (`color-light`, or `dimmer` with `switch`), `media` (`audio-stream`), `switch`, `sensor`, `other`. A device with only extension capabilities, `button` or a bare `dimmer` is `other`, never sensitive. **Sensitive categories** are `lock`, `opener`, `alarm` and `camera`: a device falls under every sensitive category any of its capabilities implies, not just its display category. The operator can raise a device's category (`oxidhome device set-category`, `PUT /api/v1/devices/{id}/category`), never lower it: a raise adds the category on top of what the host derived. The host also remembers, per device id, every sensitive category it has seen (`device_meta`, migration 21), so an `update-device` that drops `lock` doesn't drop the protection, and an instance that ever registered a camera keeps its blobs classed as camera bytes after it stops (the upgrade seeds the record from persisted `video-stream` state and events; a floor that can't be stored refuses the registration; floors and overrides commit at `synchronous = FULL`; a raise to `camera` is refused while the host can't name the device's owning instance). Pre-upgrade, the host kept no record of registered capabilities, so a camera whose bytes were persisted only under another capability is classed when its plugin next registers it. A queued command is re-authorized when the supervisor dequeues it: if the device has meanwhile gained a sensitive category its admission didn't cover, or is no longer registered, it ends `rejected` without running. The categories ride `GET /api/v1/devices`, Connect `ListDevices` and MCP `oxidhome://devices` as `category` plus a `sensitive` list.

## The host responsibilities

The host (Rust core) owns:

1. **Plugin lifecycle** — loading components, spawning instances, enforcing capabilities, restarting on crash. Each install of a plugin is stamped with a per-install `installation_uuid` persisted in the `plugin_installation` SQL table; the UUID feeds device-id derivation so that uninstalling and reinstalling the same plugin id produces distinct device ids. Uninstalled rows are tombstoned rather than deleted so operators can audit when identity rotated for a given `plugin_id`; **the tombstone table does not carry a device-id back-reference** — audit rows written against a retired install's device ids cannot be resolved back through this table (adding a `plugin_device` mapping is a C1c follow-up if that lookup becomes load-bearing). The manifest's `[capabilities]` block is the plugin's **request**; the host stores an independent **granted** copy in `plugin_installation.granted_capabilities_json` and every runtime gate (device-capability check, `subscribes-events`, storage/blob quotas) consults the grant rather than the manifest, so a future operator API can narrow the grant without editing the plugin's manifest (v1 defaults grant = request at install time)
2. **Device registry + host-owned state projection (H9)** — the registry is the canonical list of devices (IDs, names, capability specs). Host-minted device ids are deterministic: `dev-<hex(SHA-256(installation_uuid, instance_id, local_id))>`; a plugin's re-registration on restart resurrects the same id, a reinstall (fresh `installation_uuid`) mints a new one. **Current state lives in a separate host-owned projection** (`DeviceStateStore`), keyed on `(device_id, capability)` — the registry never stored state past registration-time `initial_state` (review report H2). The projection is updated via two distinct operations: `replace_snapshot` (full-state input — used by `register-device` `initial_state` and `execute-command` `OkWithState` returns) overwrites the slot; `apply_delta` (partial-changes input — used by `state-changed` events under the same `publish_sequence` gate as the event-log mirror write) merges by key so a color-light update reporting only `hue` composes with the last-known `saturation` / `value` / `color-temp-kelvin`. Choosing the wrong operation matters: pre-fix, register-device fell through the merge path so a re-register that omitted a field left the stale value present — the documented remove-and-re-register deletion procedure didn't actually delete. `OkWithState` also re-validates ownership + capability declaration after the guest returns before projecting, so a plugin that calls `remove-device` mid-`execute-command` and then returns `OkWithState` can't resurrect the removed slot. Each entry carries a store-wide `global_revision` (the sole ordering axis — a per-`(device, capability)` counter was removed in round 9 because preserving it across stale-cap eviction would either grow the store unboundedly with tombstones or force a global epoch rotation on every eviction, a `DoS` vector), host `received_ms` and plugin-supplied `observed_ms` (trust-separated, same shape as `event_log`), the supervisor `source_generation` at write time, and a `quality` marker (`fresh`/`stale`). Revision allocation and insertion linearize under one lock, and snapshot/delta reads take the same lock — a reader observing `current_revision() = N` sees every entry with `global_revision ≤ N`, and the API returns `(revision, entries)` atomically. Every response also carries an opaque `epoch` (128-bit OS-random nonce, persisted with the projection, so it changes only when the projection is discarded, e.g. a fresh state dir), and `deltas_since` returns `reset_required = true` on an above-current cursor, a below-eviction-watermark cursor (missed a stale flip), or a cursor inside a revision range a boot skipped (see *Device state (H2)* below). Lifecycle events reconcile the projection: `remove-device` flips the device's entries to `Stale`; `update-device` with a narrower `capabilities` list flips the dropped capabilities to `Stale`; `register-device` runs the atomic `reset_and_seed_device` composite — flips every pre-existing `Fresh` entry for the stable id to `Stale` and re-seeds the current registration's `initial_state`, all under one lock, so a re-register that keeps a capability but omits its initial state doesn't silently retain the pre-restart value. When the owning instance stops (or a new supervisor life begins), the supervisor calls the composite `restart_generation` — mark-stale + bump-generation under one store write lock — so no delayed writer can slip a fresh entry stamped with the pre-restart generation past the sweep. **The projection is a materialized-latest view, not an append-only stream**: a slot updated multiple times between polls has its intermediate `global_revision` values overwritten in place, so `state/changes` responses reflect the current per-slot value only. Callers who need the full history read the durable `event_log` (`GET /api/v1/events`). Snapshot API: `GET /api/v1/devices/{id}/state` returns `{revision, capabilities}` for one device; `GET /api/v1/devices/state?cursor=X&limit=N` returns a paginated full-store snapshot as `{revision, devices[], next_cursor?}` — the resync primitive a client falls back on after `reset_required`, so a `devices:read`-only client can recover without also holding `devices:list`. Pagination is by *device* (all capabilities for a given device land on the same page, so per-device snapshots stay atomic) and by *server-issued opaque cursor* that encodes epoch + pinned revision + `after_device_id`. First-page requests carry no cursor; the response returns the store's current revision as both `revision` and (embedded in) `next_cursor`. Continuation requests pass the previous `next_cursor` back verbatim; the server decodes it, verifies its epoch and per-process nonce still match the store's (409 if not — daemon restart mid-resync, restart from scratch), and echoes the pinned revision as `revision`. After the final page, the client uses that pinned revision as its `since_revision` for `/state/changes`, so writes that landed mid-pagination (including to devices already paged past or new devices sorting behind the cursor) — all of which carry `global_revision > pinned_revision` by construction — surface on the next cursor poll. Because the cursor is server-issued and epoch-verified, the client can neither omit the pin on continuation nor forge a stale one. The store's entries live in a `BTreeMap` keyed on `(device_id, capability)`, so each page's range scan is `O(log N + k · caps-per-device)` — no full-store copy per request, no lock hold beyond the returned entries. Cursor catch-up: `GET /api/v1/devices/state/changes?since_revision=N&limit=M` returns entries with `global_revision > N`, ascending. Each `(device, capability)` slot is bounded to `MAX_FIELDS_PER_SLOT` (64) distinct field keys — `apply_delta` accepts updates to existing keys freely but drops new keys past the cap, and `replace_snapshot` / `reset_and_seed_device` truncate oversized inputs — so a plugin repeatedly publishing `state-change` events with unique keys can't grow one Fresh slot without bound (that path bypasses both the per-instance device quota — only one slot — and the stale-eviction cap — never flipped stale). All three are gated on the `devices:read` scope (distinct from `devices:list` which reads the registration snapshot, and `devices:command` which drives actuation). `register-device` enforces a per-instance quota (`MAX_DEVICES_PER_INSTANCE`, currently 1024) so a plugin looping unique `local_id`s can't grow the registry (and the projection whose `Fresh` entries never evict) without bound, a per-device capability cap (`MAX_CAPABILITIES_PER_DEVICE = 32`) so one device can't grow its projection footprint via unique `extension(...)` entries, and rejects `DeviceInfo` with duplicate capability specs or duplicate `initial-state` entries so two conflicting values for the same capability can't silently overwrite each other on the projection's canonical slot. Each `(device, capability)` slot is bounded to `MAX_FIELDS_PER_SLOT` (64) distinct field keys AND `MAX_BYTES_PER_SLOT` (64 KiB) of merged value bytes, both enforced at the WIT boundary: `publish_event` for `state-changed` and `register-device` / `update-device` for `initial_state` pre-check via `DeviceStateStore::check_delta_admission` / `check_snapshot_admission` and return `WitError::InvalidArgument` before persisting (an `execute-command` `OkWithState` that fails the same checks is not projected and its command ends `outcome_unknown`, H5) to the durable event log — pre-fix, the store silently truncated overflow while the event log and bus fanout carried the full state, producing two conflicting authoritative views. Manifest validation caps `capabilities.declares_devices` at `MAX_DECLARES_DEVICES = 64` so plugin-declared capability lists can't push per-register-device admission work into DoS territory. The paginated recovery cursor is HMAC-SHA256 signed with a per-process 256-bit secret (`<epoch>.<boot>.<revision>.<device>.<hmac128>`, `boot` a per-process nonce); a client can neither forge a cursor from scratch (the epoch is public but the secret isn't) nor mutate the pinned revision or device id in an existing one, so the pin protocol's cross-page consistency guarantee holds even against a malicious client. `verify_cursor` compares the epoch and the boot nonce before validating the MAC so a legitimate cursor from a prior daemon life (rotated secret) surfaces as `EpochChanged` → 409 (restart the resync), not `Bad` → 400 (client bug). Admission for `apply_delta` mirrors the store's write-path merge-vs-replace rule (only baselines against the existing slot when it's Fresh and same-generation, else treats the incoming vec as a replace) and normalizes duplicate keys in the incoming vec to last-wins before measuring — so a post-restart delta doesn't get rejected against a stale slot's fields, and a `[a="", a=<big>]` sequence isn't undercounted by the byte cap. Snapshot inputs (`register-device` `initial_state`, execute-command `OkWithState`) also canonicalize duplicates last-wins before storing so the projection, wire response, and REST HashMap conversion don't disagree about which value is authoritative. A per-instance aggregate quota (`MAX_PROJECTED_BYTES_PER_INSTANCE = 16 MiB`) checked at admission bounds one plugin's total projected footprint regardless of how it's split across devices and capabilities; register-device runs the aggregate admission BEFORE mutating the registry (the id is deterministic, so it can be computed up front), so a rejection can't destroy pre-existing metadata via a rollback that overwrites-then-deletes. The aggregate excludes `Stale` entries — the stale-cap evictor bounds their contribution separately, and charging Stale bytes against the live quota would let one instance fill 16 MiB, mark it Stale, and lock itself out of publishing new state until the total-store stale sweep fires. `execute-command` `OkWithState` is canonicalized once (last-wins on duplicate keys) and the canonical vec feeds both the projection write AND the returned `CommandResult`, so the projection, REST HashMap conversion, and Connect RPC duplicate-preserving encoding all agree on the authoritative values. The full-store snapshot endpoint truncates each page at both a device-count cap (default 64, max 256) and a cumulative-page-byte cap (1 MiB) at device boundaries, so one request never allocates more than the ceiling regardless of how large per-device slots are. The caps are applied on the raw `Arc<DeviceState>` entries fetched from the store (cheap ref-clone), each page accumulates a *whole device* into a pending buffer and commits it as one unit at the device boundary (so a page can't silently exceed the ceiling by up to a device's capability contribution), and only the committed entries are deep-cloned into wire values — pre-fix, `DeviceStateEntry::from_state` ran on every fetched entry (up to ~128 MiB at max limit) before the byte cap truncated the response to 1 MiB. `execute-command` `OkWithState` runs the per-slot admission on borrowed data (`projected_slot_size` uses a `HashMap<&str, usize>` bounded by unique-key count, early-exits on field-count overflow — the count is monotonic — and checks bytes only after processing every duplicate, so a `[big, small]` last-wins sequence for the same key is accepted like the write path would) before the ownership/capability check, consumes the guest-returned vec (via `match` on `CommandResult`), and canonicalizes by *moving* values through the dedup pipeline (`canonicalize_owned`) — no per-`KeyValue` clone on either the reject or the accept path.
3. **Event bus** — pub/sub for state changes, button events, plugin-defined custom events. Delivery is per-subscriber (private `mpsc` queue per `subscribe*` call, filter applied before enqueue): a slow subscriber whose queue fills drops events for itself only, with a `tracing::warn` and per-subscriber drop counter — the pre-C2e shared broadcast ring would have evicted events for every subscriber on overflow. Publish is per-instance rate-limited (C2d) so a rogue plugin can't spend the delivery loop's per-second budget monopolistically
4. **Storage** — small KV per plugin instance (with quotas), plus a separate `blob-store` interface for larger data (buffered whole-blob reads and writes, Phase 5b)
5. **Configuration** — plugin instance configs, user preferences
6. **Media pipelines** — when streaming plugins describe pipelines, the host runs them natively
7. **Model registry** (0.x+) — when AI plugins request inference, the host loads/runs models natively
8. **UI / API surface** — HTTP endpoints for clients to consume, currently split across a JSON/REST + WebSocket surface and a Connect RPC surface (which speaks Connect, gRPC, and gRPC-Web off the same handlers) on one shared listener. Plugin UIs (C6) load through a two-step ticketed flow that works in real browsers. **The sandboxed iframe + typed postMessage broker is the sole path any plugin-authored UI code executes on** — Phase 13 must not offer a mode where plugin JavaScript loads directly into the shell realm (e.g. as a Web Component imported into the shell's DOM), because that would give plugin code the shell's origin, the shell's DOM, the operator's bearer, and every capability the shell holds. CSP alone is not isolation; opaque-origin iframes are. Any future extension-point contract (config panels, dashboard widgets, custom detail pages) must be defined as a message envelope on the per-plugin `MessagePort`, not as a Web-Component import surface: (1) the dashboard (which holds the bearer) `POST`s `/api/v1/plugins/{plugin_id}/ui-session` (gated on `plugins:ui`) and reads back `{url, expires_ms}` where `url` is `/api/v1/plugins/{plugin_id}/ui?tk=<opaque>`; (2) the dashboard hands that URL to the browser as an iframe `src` (or a `window.open` argument) — no `Authorization` header needed, because browsers don't propagate it to iframe subresources or top-level document navigations. `/ui` verifies the ticket and returns a wrapper page whose only body is an `<iframe sandbox="allow-scripts allow-forms">` — deliberately no `allow-same-origin`, so the browser assigns each iframe a fresh opaque origin, distinct from the daemon's and from every other plugin's. The wrapper embeds the same ticket into the inner iframe's `src="/api/v1/plugins/{plugin_id}/ui/frame?tk=<opaque>"`; `/ui/frame` verifies the ticket a second time. Both `/ui` and `/ui/frame` sit on a router *outside* the bearer middleware — the ticket is the only auth check that reaches them. Tickets are HMAC-SHA256-signed with a per-process 256-bit secret (rotated on daemon restart), 5-minute TTL, bound to both `plugin_id` and the current `installation_uuid` (so an uninstall + reinstall under the same id mints a new UUID and old tickets fail closed as 404 — same shape as "no such plugin", no enumeration oracle). Raw ticket length is capped both at the axum extractor layer (a custom `TicketQuery` that reads `parts.uri.query()` as a borrowed slice and rejects anything longer than `MAX_TICKET_LEN + "tk=".len()` before allocating the owned value) and inside the HMAC verifier (`rsplit_once` + `splitn(3, '~')`, never collects into a `Vec`), so the public `/ui/frame` verifier can't be pushed into per-request allocation growth by a huge `tk=…` value up to hyper's request-head limit. Both public endpoints verify the ticket's HMAC *before* touching the installed-plugin registry — so `?tk=garbage` returns 400 uniformly regardless of whether the URL path names an installed plugin, and even a MAC-valid but wrong-target ticket surfaces as 404 (same shape as "no such plugin"), giving unauthenticated callers no oracle to enumerate installed integrations. Every response on the three UI endpoints — success bodies, ticket errors, scope 403s excluded, 404s and 501s included — carries `Cache-Control: no-store` so a shared proxy can't replay a stored response past ticket expiry or through an uninstall+reinstall. The wrapper's inline broker JS establishes a fresh `MessageChannel` per iframe and transfers `port2` to it, so all subsequent host↔plugin IPC flows on a dedicated port — an origin-based `postMessage` filter would be useless here (opaque-origin senders all report `origin: "null"`), and the per-port binding makes cross-plugin dispatch impossible by construction. `plugin_id` is percent-encoded into the URL and HTML-escaped in every template slot to defend against a future validator relaxation that admits URL / HTML syntax. Phase 13 adds three surfaces on top of C6's substrate: (a) the `[ui]` block on the plugin manifest with validation on every asset path (same escape family as `runtime.wasm`), widget-count / duplicate checks, and a fixed enum on the three `[ui.permissions]` fields that map to CSP directives; (b) `GET /api/v1/plugins/{plugin_id}/schema` returns the manifest's `config` + `[ui]` verbatim so the shell can render declarative config forms and locate declared UI assets in one round trip (gated on `plugins:list`); (c) persistent user-composed dashboards in a new `dashboard` table (migration 15), exposed as five REST endpoints under `/api/v1/dashboards` (list / GET / POST / PUT / DELETE) gated on `dashboards:read` / `dashboards:write`. Dashboard layout is opaque bytes to the host — the shell owns the JSON tree shape, versioned by `schema_version` so a widget-catalog change can drive a shell-side migration. Cross-owner reads / writes / deletes return 404 so the multi-user follow-up doesn't leak the id-space to other operators through the status code.

## Streaming and media (the camera problem)

### The principle: control in WASM, data in native code

WASM is excellent for parsing, state machines, crypto, and small per-packet work. WASM is **bad** for video codec work — it can't see the GPU, software-decoding 4K H.265 in WASM will drop frames on commodity hardware.

Therefore: **WASM plugins describe media pipelines; the host runs them natively** (using GStreamer, FFmpeg-as-a-library, or a Rust media stack).

### The pipeline model

A streaming plugin's `setup-pipeline` returns a `media-pipeline` describing:

- A **source** — a typed RTSP or HTTP `network-endpoint` the host opens directly (TLS flag, host, port, path, and an optional `credential-ref` naming the instance-config keys that hold the username and password), or a `plugin-pipe` where the plugin produces re-framed bytes. There is no URL string and no local-file source.
- A list of **steps** — demux, decode, re-encode, transcode, filter, inference-tap. Containers, codecs, and filters are WIT enums/variants, so the allowlist is the contract.
- A list of **sinks** — RTSP mount, WebRTC track, HLS mount, recording profile. Sinks are logical names the host places in the plugin instance's own namespace; plugins never pass filesystem paths.
- An **activation policy** — on-demand, always-on, motion-triggered

### Native execution policy: in-process, with strict limits

Native media and inference run inside the host process, not in out-of-process workers ([ADR-0002](docs/adr/0002-in-process-native-media-and-inference.md)). The cost of that choice is that a native parser bug can take the daemon down, so the host validates every plugin-controlled value before native code sees it:

- **Network sources.** The host resolves the endpoint's host itself and checks every resolved address — and every redirect hop, at most 5 and never TLS → plaintext — before connecting to exactly the address it checked. Loopback, link-local, and private ranges are denied unless the plugin's grant allows that class; unspecified, multicast, broadcast, and reserved addresses are always denied. IPv6 addresses that embed IPv4 (mapped, NAT64, 6to4) are classified by the embedded address.
- **Names.** Sink names, recording profiles, and model names are `[a-z0-9_-]{1,64}`; model versions are `[A-Za-z0-9.+-]{1,32}` without `..`. None is ever used as a path.
- **Pipeline bounds.** At most 32 steps, 8 sinks, and 8 preprocessing steps per inference tap; at most 1 MiB per `pipe-writer.write`; frame sizes 1–8192 per side; frame rates finite, in (0, 120].
- **Tensors.** Rank ≤ 8, every dimension ≥ 1, ≤ 2^26 elements and ≤ 64 MiB per tensor, data length exactly elements × element width, ≤ 16 tensors and ≤ 256 MiB per `infer` call — computed with overflow-checked arithmetic, on inputs and on model outputs.

The WIT `media` and `inference` doc comments are the contract for these rules; `oxidhome_core::native_policy` implements them as unit-tested helpers. They aren't called yet because no pipeline or inference runtime exists — Phases 9 (media) and 10 (inference) run them before handing anything to native code.

### How it handles real-world cameras

| Camera type                                                | What the plugin does                                                                     | Where bytes go                                                                          |
|------------------------------------------------------------|------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| Standard ONVIF                                             | Discovers RTSP URL via WS-Discovery                                                      | Host opens URL directly; bytes never enter WASM                                         |
| Tapo / Reolink / proprietary auth + standard codec         | Runs vendor handshake, strips proprietary framing, re-frames as RTP, writes to host pipe | Bytes pass through WASM as RTP packets (cheap), host pipeline takes over                |
| Cloud-only camera                                          | Authenticates against vendor cloud, requests stream URL                                  | If standard URL: easy case. If requires vendor SDK: error, user needs the native bridge |
| Encrypted vendor stream                                    | Runs key derivation; either decrypts in WASM or hands key to host                        | Per-frame work native if decryption is heavy                                            |
| Codec mismatch (H.265 from camera, H.264 needed by WebRTC) | Pipeline includes `decode-video` + `encode-video` steps                                  | Host does both natively, with hardware acceleration                                     |
| MJPEG-only ancient camera                                  | Pulls JPEGs over HTTP, writes to host pipe with format hint                              | Host decodes/re-encodes natively                                                        |

### The native bridge escape hatch

Some cameras genuinely cannot be supported from WASM:

- Vendor SDK shipped only as closed-source `.so` / `.dll`
- Hardware decoder access requiring direct V4L2 / VAAPI / NVENC ioctls
- Protocols using kernel features WASI doesn't expose (raw sockets, multicast on specific interfaces)

For these, OxidHome supports a **native bridge plugin** type — a separate subprocess running under OS-level sandboxing (separate user, seccomp profile, network namespace), talking to the core over a defined IPC protocol (gRPC or Cap'n Proto over Unix socket).

This is **explicitly marked in the UI** as native code requiring user trust. WASM is the default and covers >90% of integrations; native is for the irreducible exceptions.

## AI / ML plugins

### The same pattern as cameras: control in WASM, computation in native

WASM cannot effectively run real-time ML inference on video. wasi-nn lets WASM plugins request inference from a host-managed runtime, which is the right model.

### The three AI patterns OxidHome supports

| Pattern                                 | Where it runs                                                                                                    | When to use                                     |
|-----------------------------------------|------------------------------------------------------------------------------------------------------------------|-------------------------------------------------|
| External AI service                     | Plugin is a thin HTTP client to Frigate/Ollama/CodeProject.AI/cloud APIs                                         | Day one. User runs the AI service themselves.   |
| Host-managed model + WASM orchestration | Plugin requests model, host runs it natively (ONNX Runtime / TensorRT / Core ML / OpenVINO), plugin gets results | Polished real-time inference. Some 0.x version. |
| Native AI bridge                        | Closed vendor SDKs, exotic accelerators                                                                          | Last resort, same shape as native camera bridge |

### The `inference-tap` pipeline step

For real-time video AI, plugins don't pull frames into WASM. Instead, the pipeline includes an `inference-tap` step:

```
Camera → Decode (native) → Inference Tap (native, GPU) → ...
                                ↓
                          Plugin gets results
                          as events (small payload)
```

The plugin sees only structured inference results (bounding boxes, labels, confidences) — a few hundred bytes per frame, not a megabyte of RGB. The plugin's job is the *interesting* part: filtering, debouncing, deciding what counts as an "event," ignoring zones, weighting by motion.

### Models as platform resources

Models are **first-class platform resources**, not application code shipped inside plugins:

- Host has a **model registry** with versioned, signed model files
- Plugins declare model dependencies in their manifest
- Multiple plugins can share a model (one copy in GPU memory)
- The host abstracts hardware backends (CUDA, ROCm, Metal, OpenVINO, CPU)
- Plugins are not coupled to specific accelerator SDKs

This avoids both the "every plugin ships its own copy of YOLO" problem and the "plugins are a side-channel for arbitrary GPU code" problem.

### Trust and safety for models

Loading a model is asking the host to execute computation on the GPU using arbitrary weights. Defenses:

- Models in the official registry are signed and reviewed
- Plugin manifests declare which models they need; user approves at install
- ONNX-only as the model format (well-defined operator set; no arbitrary code paths)
- Resource limits on inference (max memory per model, max time per call) and validated tensor shapes and sizes (see [Native execution policy](#native-execution-policy-in-process-with-strict-limits))
- User-provided models always supported as an escape hatch (drop ONNX in `/var/lib/oxidhome/models/`)

### Hardware backend strategy

- **Day one**: ONNX Runtime with CPU execution provider, plus optional CUDA and Core ML where toolchain permits
- **Later**: pluggable execution backends (TensorRT, OpenVINO, Hailo, Coral) that users opt into
- **Never**: silent fallback. If a model can't run on the user's hardware, fail clearly. Don't have someone's NVR cooking on CPU because their CUDA install was broken and we didn't tell them.

## Communication patterns

### Host → Plugin

- **Lifecycle** — `init()`, `on-shutdown()`. The shutdown export is named `on-shutdown` because a bare `shutdown` core symbol collides with wasi-libc's socket `shutdown(fd, how)`; the SDK still exposes it to plugin authors as `Plugin::shutdown`.
- **Event delivery** — the host buffers matching events on the subscriber's per-instance queue. A host-side helper (`PluginInstance::drain_events()`) walks that queue and invokes the plugin's `on-event` export once per buffered event. There is no separate `drain-events` export on the plugin world. Since Phase 6 the per-instance supervisor task owns the `Store` and calls it: it `select!`s between control commands, ticks and bus wakeups (a wakeup fires only for a publish matching one of the plugin's filters) and drains after `init` and after every loop step. The polling-drain shape preserves the single-threaded per-`Store` WASM contract — no host call ever re-enters the plugin from a separate task — and avoids needing a streaming export on the plugin world.
- **Commands** — `execute-command(device, cmd)` for actions targeting plugin's devices (`cmd.id` is the host-minted command id; see [Command outcomes (H5)](#command-outcomes-h5)); `execute-service-command(service, command, args)` for actions targeting the plugin's services (Phase 7), routed from the host dispatcher
- **Periodic** — `tick()` for plugins that genuinely need a heartbeat (most should be event-driven). A streaming instance with a tick cadence is also ticked early when a socket it holds open becomes readable (see *Network access (Phase 8)*).

### Plugin → Host (imports)

- **Device lifecycle** — `register-device`, `update-device`, `remove-device`, `get-device`; `complete-command` finishes a command the plugin answered `accepted` (H5)
- **Service lifecycle** (Phase 7) — `register-service`, `update-service`, `remove-service`, `get-service`; gated by `[capabilities] declares_services`
- **Script sandboxes** (ADR-0001) — `start-sandbox`, `stop-sandbox`, `list-sandboxes`, `current-sandbox`; gated by `[capabilities] script_sandboxes`
- **Event bus** — `publish-event`, `subscribe`, `unsubscribe`; `read-events` replays recorded events the plugin's subscriptions match (see *Plugin history reads* under [Event delivery](#event-delivery))
- **Storage** — `get`, `set`, `delete`, `list-keys` (small KV, per instance); blob bytes via the `blob-store` interface
- **Configuration** — `get-config`, `list-config`
- **Device state** (H2) — `host-state::get-state`, `list-state` read the host's state projection; own devices always, others with `[[capabilities.reads_state]]` (see *Device state (H2)*)
- **Network** (streaming worlds only, Phase 8) — WASI 0.2 `wasi:sockets` and outgoing `wasi:http`, checked against the instance's `[capabilities] network` rules (see *Network access (Phase 8)*)
- **Inference** (AI plugins only) — `load-model`, model handles with `infer()`
- **Logging** — at standard levels

### Plugin → Plugin (Phase 7)

- **Service dispatch** — `host-services::call-service(target, command, args)` is a synchronous host-mediated call. The host resolves `target` (a `service-id` minted by `register-service`) to its owning instance, looks the instance up in the engine's registry, and hops to that instance's Phase-6 supervisor task to invoke its `execute-service-command` export. The single-`Store` contract holds: a callee's wasm only ever runs on its own supervisor task.
- **Stable, immutable resolution (H10)** — `service-id` values are per-run: the host mints a fresh `svc-N` on every `register-service` call, so callers that persist a target across restarts persist the three-tuple `(plugin-id, instance-id, service-local-id)` and re-resolve on demand via `host-services::resolve-service`. All three components are stable. The address uses the callee's **immutable `local-id`** (the plugin's own bookkeeping key from `service-info.local-id`), not the human-readable `name` — `register-service` refuses a duplicate `(instance, local-id)` and `update-service` refuses any change to `local-id`, so a persisted address cannot silently invalidate under a rename.
- **Caller-side capability gate (H10)** — before routing, the dispatcher matches the target service's `(owner_plugin_id, owner_instance, local_id)`, the requested command name, **and the actual caller's instance-id** against the caller's structured `[capabilities] consumes_services` grants. Each grant is a resource selector `{plugin, instance, service, commands, caller_instance}`; `instance`, each entry in `commands`, and `caller_instance` may be `"*"` to match any target instance / any command / any caller instance. Because the authorization keys off the immutable `local-id`, a callee that renames its service via `update-service` cannot silently bypass or shadow a grant. The `caller_instance` axis is what stops a grant on one instance of a multi-instance caller plugin from authorizing every other instance of the same plugin — plugin manifests typically leave it `"*"` and operators narrow it in the granted copy. `"*"` is reserved as the wildcard sentinel at identifier boundaries: `Engine::start_instance` refuses `"*"` as an instance-id, and `register-service` refuses `"*"` as a command name, so a real identifier can never collide with the wildcard.
- **Grant application (requested ∧ granted, no cross-product)** — a call is authorized iff at least one entry in the plugin-declared **requested** list matches AND at least one entry in the operator-narrowed **granted** list matches (H10 round-4). Both checks run at call time against the target-tuple; no materialized intersection is stored. This is semantically equivalent to requested ∩ granted but avoids the O(N²) blowup a cross-product would produce when a manifest declares N wildcard-target selectors × N wildcard-caller selectors (each pair produces a distinct narrowed record). Manifest validation caps `consumes_services` at [`MAX_CONSUMES_SERVICES_GRANTS`] entries with each grant's `commands` capped at [`MAX_COMMANDS_PER_GRANT`], so the per-call check is bounded per instance. `effective_capabilities` carries only the granted list on the intersected `CapabilitiesSection`; the requested list rides separately on `PluginState`.
- **Same-instance dispatch is not supported** — the callee's supervisor drives exactly one wasm `Store`; a dispatch to a service the caller's own instance owns would queue an `ExecuteService` to a supervisor already parked awaiting the caller's reply, deadlock-by-construction. The dispatcher rejects the `caller_instance == target_instance` case up-front with `Error::InvalidArgument` and the message `same-instance dispatch is not supported`; plugins that colocate multiple services in one instance dispatch between them in plugin-local code without going through `call-service`. Scripting plugins run each script in its own sandbox instead (see *Script sandboxes* below), so script-to-script calls are ordinary cross-instance calls.
- **Cycles** — the dispatcher carries the in-flight call chain across the task hop as the delegation chain of the callee's `InvocationContext` (in `ControlCommand::ExecuteService`); the callee's supervisor re-scopes it as a `tokio::task_local` on its task before driving the wasm so any nested `call-service` sees the full chain. Multi-hop A→B→…→A calls are rejected with `Error::InvalidArgument` and the message `cycle detected` — distinct from the same-instance case so operators can tell them apart in logs.
- **Root attribution and deadline (H6)** — every hop inherits the invocation's root principal, call id and deadline (see *Invocation context* below). The dispatch timeout (and the hop's audit writes) are clamped to the remaining deadline, a hop is refused once the deadline has passed, and the callee's context carries the hop cutoff so its supervisor drops a queued hop the caller already stopped waiting for.
- **Typed command schemas (M2)** — every `command-spec` declares machine-readable `params` and `returns` lists of `field-spec`s (name, `value-kind`, required, optional `one-of` / `int-range` / `float-range` constraint); descriptions are informational and never parsed. `register-service` / `update-service` refuse a malformed schema (bad or duplicate names, a constraint that doesn't fit the kind, inverted or non-finite bounds, size caps) with `invalid-argument`. After the grant check, the dispatcher refuses a command the service doesn't declare and `args` with duplicate, undeclared, missing-required, mistyped, out-of-range, or invalid-JSON fields with `invalid-argument`, before the callee's wasm runs; the callee's `ok-with-state` reply is checked against `returns` and a violation reaches the caller as `internal`. A plugin's `execute-service-command` therefore only sees declared commands with well-typed arguments (`runtime::schema`). Args and reply are checked against the registration snapshot the dispatcher read when the call was admitted; a callee that changes its own schema with `update-service` while calls to it are queued handles those calls under the schema they were admitted with. On an externally-rooted invocation a schema refusal writes no H6 hop row, like the other non-authorization refusals (same-instance, cycle, expired deadline, owner not running); a `returns` violation finalizes the hop row as `allow` / `failed` / `internal`, since the callee did run.
- **Script sandboxes (ADR-0001)** — a scripting-plugin instance starts one child instance per user script with `host-sandboxes::start-sandbox(local-id, source)`: the same component and pinned manifest, under the parent's load mode and effective capabilities, with its own `Store`, supervisor, restart policy, watchdog and C4 ceilings. The child's instance id is `<parent>~<local-id>` (`~` is refused in operator-chosen ids), and it reads its script with `current-sandbox`. A script registers its commands as a service in its own sandbox, so script A calling script B is a cross-instance `call-service` with the usual grants (per-script narrowing through the `instance` / `caller_instance` axes), cycle check, deadline and H6 hop rows. `[capabilities] script_sandboxes` (≤ 64, min of requested and granted) caps live sandboxes per parent. A sandbox's crash restarts only that sandbox; sandboxes survive a parent restart (a same-source `start-sandbox` re-adopts them) and are stopped when the parent reaches a terminal state. The parent's supervisor compiles the component once and its restarts, sandboxes and their restarts reuse it. `stop-sandbox` removes the script: once the sandbox is gone (and any storage write it left running has finished) its KV and blob storage are purged and its device-state generation and publish rate limiter dropped (a sandbox stopped with its parent keeps them). A persisted `sandbox_removal` marker (migration 22) keeps the `local-id` blocked until the purge succeeds; an unfinished purge runs again at the next boot. Instance listings (REST, Connect, MCP) show a sandbox's `parent_instance_id` and `sandbox_local_id`. `runtime::sandbox`; [ADR-0001](docs/adr/0001-one-sandbox-per-script.md) has the implementation notes.
- **A callee trap is `unknown` (H5)** — if the callee traps after a call reached it, the caller gets `command-result::unknown` (it may have acted) and the callee restarts under its own policy; a call refused before it reached the callee (owner not running or restarting, deadline passed before dequeue) is `unavailable` and never ran. A dispatch timeout is `unavailable` only while the call is still queued; once the callee started it, the caller whose wait ends gets `unknown`, and a result produced afterwards is recorded as a `CALL_RESULT` row.
- **Back-pressure** — a registry refcount makes `remove-service` refuse with `Error::Unavailable` while a call is in flight; the refcount travels with the work (in the control-channel message), not with the caller's wait future, so a dispatch-side timeout can't release it mid-handler.

### Long-running work

- Most plugins are event-driven (subscribe + react)
- Streaming plugins use Wasmtime's async host function support — calls suspend without burning CPU
- Plugins that genuinely need polling implement `tick()`; the host calls it on a schedule from the manifest

## Implementation decisions

Settled engineering choices that shape the codebase, captured here so they survive when transient planning docs do not.

### Bindgen and publication

- **`oxidhome-wit`** — the single bindgen crate, with **per-world Cargo features**: `plugin`, `streaming-plugin`, `ai-plugin`, `streaming-ai-plugin`. Each world's module tree is `#[cfg(feature = "...")]`-gated so a plugin that only uses one world doesn't trip `wasm-component-ld`'s "multiple component-type metadata sections" linker error. Host and SDK both depend on it.
- **Publication policy.** Every workspace crate (`oxidhome-wit`, `oxidhome-sdk`, `oxidhome-core`, `oxidhome-manifest`, `oxidhome-proto`, `oxidhome-test-host`) carries `publish = false` through 0.x. Versions live only in the root `Cargo.toml`: members inherit `version.workspace = true`, and internal crates are path-only `[workspace.dependencies]` entries (a `version` requirement gets added back when they flip publishable). External dependency versions are likewise declared only in the root `[workspace.dependencies]`; crates use `<dep>.workspace = true` and may only add features. Path dependencies and a workspace-root `wit/` directory make publishing impossible without packaging changes anyway, and pre-1.0 we want zero friction iterating on the WIT. They flip publishable together at the first SDK release intended for external plugin authors. Re-evaluate sooner only if a second-language SDK (Go, JS) needs a versioned `oxidhome-wit` artifact to bindgen against.
- **Exact-pinning policy.** `wit-bindgen` (used by `oxidhome-wit`) and `wasmtime` (used by `oxidhome-core`) are pinned because silent minor bumps can change generated bindings or runtime embedding behavior.

### Observability

- **`tracing` for logging — never `log`.** Spans cross every host-call boundary from Phase 2 onward; retrofitting is painful. From Phase 5c, a SQLite-backed `tracing::Subscriber` layer also persists structured events so they're queryable through the CLI/API.

### Async + Wasmtime embedding

- **Wasmtime async + tokio.** Single tokio multi-thread runtime in `oxidhome-core`, entered via `#[tokio::main]` in the host binary; host imports rely on the ambient runtime that installs. Plumbing a `tokio::runtime::Handle` through the Wasmtime store data so host imports can cleanly spawn background work without leaning on the ambient runtime is an open Phase-2 follow-up (see the open question in the `oxidhome-core` per-crate plan).
- **Single-threaded contract per `Store`.** One `wasmtime::Store` per `PluginInstance`. Concurrent invocations of the same instance are serialized; cross-instance work runs in parallel.
- **`bindgen!` async syntax** is `imports: { default: async }` (modern wasmtime), not the deprecated `async: true`.
- **Resource-path syntax** in `with:` mappings uses `interface.type` (dot), not `interface/type` (slash): e.g. `oxidhome:plugin/media.pipeline-handle`.

### Time source

- **One clock per engine.** Every time decision the runtime makes about a plugin reads the `Engine`'s `oxidhome_core::clock::Clock`: event receive times, device-state `received_ms`, audit-row times, the guest's `wasi:clocks` wall and monotonic clocks, the supervisor's `tick_interval_ms` schedule and the gap before a streaming instance's early tick, the `accepted`-command TTL (H5), the per-instance publish and log rate buckets, the sensitive-action (H6) rate buckets, a streaming instance's network-policy clocks (the resolved-address grant TTL and the denial-audit rate bucket), and the liveness watchdog's epoch counter. The guest clocks are installed in every world's WASI context, the streaming world's included. The daemon always runs `Clock::system()`, which calls exactly what those sites called before the seam (`SystemTime::now`, Tokio's `Instant`, `sleep_until`, an `interval_at` with `MissedTickBehavior::Delay`, Wasmtime's default WASI clocks, the epoch-ticker thread).
- **`VirtualClock` is the test seam.** `Engine::with_state_dir_and_clock` takes one; `oxidhome-test-host` builds a host on it with `TestHost::with_virtual_clock`. Time then moves only when the test moves it: `TestHost::advance` fires the timers that fall due one deadline at a time and waits for the work each triggers, so ticks, TTL expiries, and watchdog interrupts are deterministic. Still on real time under a virtual clock: a guest's WASI sleep, request and `call-service` deadlines (H6), the event-history read deadline, restart backoff, shutdown grace periods, and KV, blob, `device_meta`, log-store, and command-journal row times (including the `COMMAND` audit rows the journal writes), retention cutoffs (the test host runs no retention), the API and MCP surfaces' relative time filters (`since=1m`), and a streaming instance's network I/O deadlines (DNS lookup, TCP connect, HTTP first-byte and between-bytes timeouts), which bound real sockets.

## Current safety invariants

Load-bearing invariants the codebase depends on today. Each corresponds to a shipped review fix or Phase decision — they are what the runtime, API, and storage layers assume when routing untrusted plugin work.

### Identity and grants

- **`installation_uuid` is the source of identity.** Every `install` mints an opaque `inst-<32 hex>` UUID and persists it on the `plugin_installation` SQL row. Uninstall tombstones the row; a subsequent reinstall mints a fresh UUID. Device IDs derive from the UUID (not from `plugin_id`), so an uninstall + reinstall cannot inherit device identity or audit lineage from the previous installation. **C1 / C1b.**
- **Granted capabilities are authoritative; requested capabilities are not.** `plugin_installation.granted_capabilities_json` is what the runtime consults at every capability gate. The manifest's `[capabilities]` block is a *request* — the loader computes `effective = requested ∩ granted` so a stale grant that is broader than the current manifest cannot authorize newly-requested permissions. **C5.**
- **Grants are content-bound.** `plugin_installation.content_digest` is a domain-tagged SHA-256 over `(manifest bytes, wasm bytes)`. The loader recomputes; on any mismatch it **rejects the load** with a "content digest mismatch — reinstall to re-issue the grant" error rather than degrading to a synthetic identity. **C5 review F3.**
- **Quarantine is fail-closed.** A live `plugin_installation` row with a NULL / malformed `granted_capabilities_json` or NULL `content_digest` is quarantined at scan: absent from `entries` so `start_instance` cannot launch it, but still `is_quarantined()` so raw-path CLI loads whose manifest declares the same `plugin_id` refuse rather than shadow the persisted grant. An operator's `uninstall` + `install` cycle re-issues both fields together. **C5 review F1.**

### Lifecycle serialization

- **`plugin_id` load provenance is explicit.** `Engine::start_installed_instance` (API path) carries the observed `installation_uuid` into the loader as `LoadMode::Installed`; `Engine::start_instance` (dev / argv) uses `LoadMode::Dev`. The loader fails closed under `Installed` if the registry row named by the expected UUID is missing, its path changed, or the UUID rotated — no silent fallback to a synthetic identity. **H11 review F1.**
- **Start and uninstall of the same `plugin_id` serialize.** `Engine::plugin_lifecycle_lock(plugin_id)` returns an `Arc<tokio::sync::Mutex<()>>`; both JSON and Connect handlers hold it across the running-instances check + the compose work. `uninstall` moves an owned guard into its `spawn_blocking` closure so a cancelled handler cannot release the reservation while the detached FS + SQL work is still running. Map entries are `Weak` so nonexistent-id requests don't grow the map without bound. **H3 + H3 review F1/F2.**
- **Uninstall is retryable and cannot orphan state.** `Engine::uninstall_plugin` resolves the `installation_uuid` from either the live-entries map OR the quarantined map (`installed_plugins.installation_uuid_for(plugin_id)`), then purges per-install KV rows + blob dirs *before* tombstoning the registry row. Quarantined installs get the same purge path as live installs. On any purge error the row stays live and the API returns the error, so the operator can retry — no silent stranding of blob bytes. **H2 review F2 + H12 review F1.**

### Per-instance state

- **KV, blob-index, and blob directories key on `(installation_uuid, instance_id)`.** Migration 14 rekeyed the four state tables (`kv`, `kv_usage`, `blob`, `blob_usage`) with a composite PK; the FS layout is `<state_dir>/blobs/<installation_uuid>/<instance_id>/`. An uninstall + reinstall of the same `plugin_id` mints a fresh UUID and therefore an empty per-instance keyspace. `purge_installation` on both stores handles the wipe. **H2.**
- **Instance IDs are FS-segment safe.** `is_safe_instance_id` — 1..=128 bytes, no `/`, `\`, `..`, leading `.`, or `\0` — is enforced at the API edge (`start_plugin_instance` returns 400) and again in the blob store as belt-and-suspenders. Every `BlobStore` entry point refuses an unsafe id before any path construction. The KV store trusts the id (it never touches the filesystem), so its check lives at the API edge only. **H1 + H1 review F1.**
- **Duplicate manifest IDs quarantine every path.** A scan that sees two directories declaring the same `plugin_id` stores ALL paths on the `QuarantineEntry`; a single `uninstall` removes every path in one call so no leftover directory survives to be backfilled on the next scan. **H8 + H8 review F1.**
- **Legacy blob directories are reclaimed once.** `Engine::with_state_dir` runs a one-shot sweep of `<state_dir>/blobs/` when `Db::pre_open_user_version() < 14`, so the pre-migration-14 flat layout doesn't leak bytes forever. Post-14 boots skip the sweep so dev-load blob dirs survive. **H2 review F3.**

### Backup, restore, and migrations

- **Backups are a consistent snapshot of the database and the files it indexes.** `oxidhome backup <out-dir>` (the target must be outside the state dir) runs online (no state-dir lock; it holds `.oxidhome-backup.lock` shared, which excludes only a restore): `VACUUM INTO` gives a point-in-time copy of `oxidhome.db` including committed WAL frames, switched to a rollback journal so the archive is one self-contained file. The blob and plugin file lists come from that snapshot, not the live tables; blob files are immutable once their row commits, so copying exactly the referenced files reproduces the snapshot (orphan files are skipped). Packages are archived from `plugins/<plugin_id>/` and must hash to their row's `content_digest`. A referenced file that vanishes mid-copy, a package that doesn't match its digest, or a live plugin set that changes before the copy finishes discards the attempt and retries (3 attempts, then the backup fails and asks for a quieter moment or a stopped daemon). Every file is listed in `manifest.json` with its size and SHA-256; the archive is built in a hidden sibling, self-verified, fsynced and renamed into place, with `0700` / `0600` permissions. It never contains the plaintext `admin-token` and is not encrypted (M7). **M3.**
- **Restore verifies everything before it touches the state dir, and keeps the old state.** `oxidhome restore <dir>` holds the exclusive state-dir lock (daemon stopped) and the backup lock exclusively, refuses an archive located inside the state dir, and checks checksums, that the archive holds exactly the listed files (no symlinks, no path traversal), `PRAGMA integrity_check`, the schema version (newer than the binary or older than v16 is refused), that the `blob` rows and the blob files match one-to-one at the recorded sizes, and that every live `plugin_installation` row has a package matching its digest. It then stages the archive, re-hashing every file and re-running the database and index checks on the staged copy, writes a durable `.restore-journal`, moves `oxidhome.db` + `-wal` / `-shm`, `blobs/` and `plugins/` into `pre-restore-<unix_ms>/` (WAL first, so stale frames can't replay onto the restored file) and the staged copies into place, renames the journal to `.restore-audit-pending`, and boots an engine on the result to write a `cli.state.restore` audit row before dropping that marker (a failure there is retried by `--resume`, never lost). While the journal exists `Db::open_file` refuses the state dir; `oxidhome restore --resume` rolls the swap forward idempotently. `oxidhome verify-backup <dir>` runs the same checks read-only. **M3.**
- **Migrations have a preflight and a forward-first recovery policy.** Before applying pending migrations to an existing database, `Db::open_file` runs `PRAGMA quick_check` and writes a `VACUUM INTO` snapshot to `<state_dir>/pre-migration/<unix_ms>-v<from>-to-v<to>.db` (newest three kept); if either fails, nothing is migrated. Each migration commits in its own transaction, so a failing migration leaves the database at the last good version and the daemon refuses to start — the fix is a binary with a corrected migration. A database newer than the binary is refused (no silent downgrade). Rolling back to an older binary instead means, with the daemon stopped, moving `oxidhome.db` and its `-wal` / `-shm` aside and copying the pre-migration snapshot to `oxidhome.db`; migrations don't touch blob or plugin files, but every write since the upgrade is lost (and rolling back across migration 14 also loses the legacy blob files its one-shot sweep removed), so this is the last resort. **M3.**

### Storage connections (M6)

- **One writer, pooled readers.** `Db` owns one writer `Connection` behind a mutex; every write goes through it, so commit order is mutex order and `BEGIN IMMEDIATE` never races an in-process writer. A file-backed `Db` also opens up to `READ_POOL_SIZE` (4) reader connections lazily, each with `query_only = ON`. `Db::read` runs its closure on a pooled reader inside one deferred read transaction, so a query sees a single committed snapshot (the isolation the old single mutex gave) and never waits on the writer. Event history, log, audit and token-list queries, token lookup, KV and blob-index reads, dashboard and registry reads all take this path. Blob byte reads stay on the writer: `BlobStore::read`, `read_by_name` and `read_with_info` look up the blob row and open its file under the writer, because a pooled snapshot can predate an overwrite or delete that unlinks the old file before the open. With the writer held nothing can supersede the row, so the open descriptor pins one complete version (old or new) or the lookup returns `NotFound`; the bytes are read after the writer is released. Readers start only after migrations apply. `:memory:` databases are private to one connection, so they have no pool and reads share the writer.
- **Writer priority.** `Db::write` is normal priority: event-log mirror writes, KV, audit, tokens, registry, dashboards, device-state flushes (H2). `Db::write_low_priority` is for work nobody waits on: diagnostic log batches and retention of the event log, the diagnostic log and the audit ledger (2048-row chunks; the event log's are H4's prefix-only trim, each deleting the lowest remaining ids, so every committed chunk and every reader snapshot has still pruned an id prefix). `Db::write_low_priority_unless` is the same with a cancellable wait: a caller whose `cancelled` check turns true (re-checked when `Db::wake_low_priority_writers` wakes the queue) leaves the queue without running. Ownership of the writer is decided by one admission gate: when the writer frees up, a queued normal-priority caller goes first, even if a low-priority caller queued earlier. A low-priority caller goes when no normal-priority caller is queued, or once it has deferred for `LOW_PRIORITY_MAX_DEFER` (250 ms). An overdue low-priority caller gets the next turn after a normal-priority transaction, and a queued normal-priority caller gets the turn after a low-priority one: neither class starves, and while normal-priority callers are queued, consecutive low-priority transactions always have a normal-priority one between them. The guarantee is per class, not per caller: within the normal class admission is not FIFO, so an individual normal-priority caller has no fixed bound on how many transactions run ahead of it. Once a low-priority transaction has the writer, a normal-priority write waits for that one transaction, so low-priority work is kept to bounded transactions.
- **Retention runs periodically for every append-only table.** The HTTP daemon and `mcp-stdio` both start `Engine::spawn_retention` (`state::retention`): per table, a pass one minute after start and then hourly deletes rows older than a maximum age or beyond the newest maximum row count. Limits come from the environment, `0` disables either, and a value that isn't a non-negative integer (including a non-Unicode one) fails startup:

  | Table | Age variable (default) | Row variable (default) |
  | --- | --- | --- |
  | `event_log` | `OXIDHOME_EVENT_LOG_RETENTION_DAYS` (30) | `OXIDHOME_EVENT_LOG_MAX_ROWS` (1,000,000) |
  | `log_event` (diagnostic logs) | `OXIDHOME_LOG_RETENTION_DAYS` (30) | `OXIDHOME_LOG_MAX_ROWS` (1,000,000) |
  | `audit_event` (audit ledger) | `OXIDHOME_AUDIT_RETENTION_DAYS` (365) | `OXIDHOME_AUDIT_MAX_ROWS` (1,000,000) |

  Diagnostic-log and audit retention are new defaults: an existing install that never deleted either table loses rows past those limits on the first pass after upgrading; set the variables to `0` to keep everything. A pass plans on a pooled reader and deletes on the blocking pool, one low-priority transaction per chunk of 2048 rows. The event log deletes only an id prefix (H4): one boundary id, the larger of the age bound (the first row received at or after the cutoff, so a clock-rollback row waits for the rows before it) and the row bound (the newest-`N` cutoff, found with an index scan only when the retained id span exceeds the limit), with each chunk deleting the lowest remaining ids. The diagnostic log and the audit ledger have no ordering contract: a chunk looks at the next 2048 ids up to the pass's highest due id and deletes the due rows among them, and the newest row always stays so ids aren't reused. The audit ledger keeps rows an unfinished write still needs: a pending row (`finalized_ms` NULL) written by the running process, which its request may still finalize, and an `accepted` device-command row whose `COMMAND` resolution row (same `call_id` and `command_id`) hasn't landed (H5); a resolution row in turn waits for its `accepted` row to go first, so a clock rollback can't strand an accepted row without its resolution, and while a pending row of the running process shares its `call_id` (a command that resolved before its request was finalized). The "abandoned or not" boundary is the highest audit id when the process first opened the ledger. A pending row from an earlier process (an abandoned request) is deleted by age only, never by the row limit. The row limit picks the newest rows by id, kept rows included; kept rows older than that stay on top of it. Shutdown stops each task between chunks and cancels a chunk still waiting for the writer (`Db::write_low_priority_unless`), then waits up to 5 s for a chunk already running. A failed pass logs a WARN and the next one runs on schedule.
- **Diagnostic logs are batched.** The log writer thread drains whatever queued while the previous commit ran, up to 256 rows, and commits it as one `BEGIN IMMEDIATE` transaction. There is no artificial linger, so an idle store still writes each row promptly. A failed batch counts every row in it as a write error. Retention (above) deletes in 2048-row chunks, each one low-priority transaction. The diagnostic log stays drop-tolerant (bounded channel, drop counter).
- **`last_used_ms` is coalesced.** A token's `last_used_ms` is written when it is NULL (first use, which the bootstrap reconciliation and `delete_undelivered` key on) or older than `LAST_USED_RESOLUTION_MS` (60 s). A busy client costs one write per minute, not one per request. The UPDATE re-checks that condition under the writer, so concurrent verifies that all read a stale value write once, and an older timestamp never overwrites a newer one. The MCP path already holds the row from its read-only pre-verify: it skips the blocking hop when that row's value is current, and otherwise coalesces on the newer of the row's value and the process's own last write. The MCP bump stays best effort: when the MCP pre-admission cap is saturated it is skipped, including on a token's first use, as before M6.
- **Audit and durability are unchanged.** Audit writes stay normal priority, unbatched, and two-phase. `record_intent` fails closed. `record_intent_durable` and M4's token writes raise the writer to `synchronous = FULL` for their one transaction and restore `NORMAL`. Readers and the checkpointer never change `synchronous` on the writer.
- **Busy and checkpoint policy.** Every connection (writer, readers, checkpointer) sets `busy_timeout = 5 s` (`BUSY_TIMEOUT`). In one process the writer mutex already serializes writes, so this covers other processes on the file (an online backup's `VACUUM INTO`, an operator's `sqlite3`) and WAL recovery. Routine checkpoints run off the commit path: a checkpointer thread with its own connection runs `PRAGMA wal_checkpoint(PASSIVE)` every 10 s (`CHECKPOINT_INTERVAL`). Passive checkpoints never take the writer lock and never wait on readers. The writer's `wal_autocheckpoint` is raised to 16384 pages (64 MiB), so a committing writer (an event publish holding the bus gate) runs a checkpoint only if the checkpointer falls far behind. That can happen when a long read keeps an old snapshot pinned: a passive checkpoint can't copy frames a reader still needs, and once the WAL passes 16384 pages each commit attempts a passive checkpoint until the WAL can reset. Reads are short, single-closure transactions, so this stays a backstop. `journal_size_limit = 64 MiB` truncates a burst-grown `-wal` when it resets. The checkpointer is stopped and joined when the `Db` drops, so no connection outlives it. Backups (`VACUUM INTO` from a fresh connection) and the migration preflight (on the writer, before readers start) are unaffected.
- **The state-dir lock outlives every write.** Both long-running modes keep the exclusive state-dir lock in a static that is never dropped, so only the operating system releases it, when the process ends. After the bounded shutdown steps (supervisors; up to 2 s for the `deny` audit rows still queued for the background audit worker, from H2 `get-state` and `read-events`; retention; the final device-state flush and the H5 command-journal close, each draining for up to 5 s with a further second allowed for its thread to start; the log flush) the runtime shuts down with a 10 s bound, counted from when the mode returns, for blocking-pool work still running (a lifecycle operation, an audit row, a retention chunk), and the process exits. Before, the lock was released when the mode returned, ahead of the runtime teardown, so a write still running on another thread (a retention chunk or an orphaned H3 mirror write on a hung disk, the checkpointer) could touch the database after a restarted daemon or `oxidhome restore` took the lock; and the teardown had no bound.
- **What is still shared.** A slow disk still slows every writer, and the H3 bus gate still serializes publishers behind one mirror write at a time. M6 removes reads and diagnostic logs from that path; it doesn't add a second writer. See [ADR-0008](docs/adr/0008-sqlite-connection-model.md).

### Event delivery

- **Per-subscriber `mpsc` queues.** Each subscriber owns a 256-slot `tokio::sync::mpsc` channel; back-pressure on one subscriber drops events **for itself only** (per-subscriber `dropped` counter + rate-limited warn). No shared broadcast ring where a slow tail client can evict events from the plugin supervisor. **C2e.**
- **Wake registration is filter-scoped.** `EventBus::subscribe_with_wake` pairs a `Notify` with the subscription filter; publishes signal only wakes whose filter matches, so a supervisor whose plugin has no subscriptions is quiet under any flood. **C2d.**
- **Per-instance publish rate limit.** `admit_publish(instance_id)` throttles at a bounded arrival rate (`DEFAULT_PUBLISH_RATE_PER_SEC` / `DEFAULT_PUBLISH_BURST`) *before* the durable log write, so a flooder can't spend disk + threads freely. **C2d.**
- **Lag is folded into the event slot.** `SubscriberMessage::Event { event, skipped_before }` — one slot per publish. A freed slot always delivers a real event; a separate `Lagged` marker slot could steal that free slot and starve fresh events indefinitely under a chronic tight-capacity workload. Wire receivers translate `skipped_before > 0` into the Connect `Lagged` body / JSON `{"lagged": N}` frame ahead of the event (with the H4 resume cursor, below). **H4 + H4 review F1.**
- **`pending_lag` accounting is race-free vs the next successful delivery.** Each `Subscriber` holds a `send_gate: std::sync::Mutex<()>` that serializes the `claim (swap 0) + try_send + reinject` triple in `EventBus::publish_with_id`. Concurrent publishers can't interleave — either A completes first (its event carries the accumulated N) or B completes first (fresh event, `skipped_before = 0`) — so the "next successful send surfaces the complete gap" invariant holds. The critical section is O(1): one atomic swap + one non-blocking `try_send` + at most one `fetch_add` on the error path. The pre-fix load-then-`fetch_sub` shape let two publishers each load the same count and each subtract it, wrapping the counter near `u64::MAX`; the atomic swap closed that, and the gate closes the interleave that let a stale `pending_lag` batch surface *after* a fresh event. **H4 + H4 review F1 + H12 review P2.**
- **Durability policy: live delivery never waits on history (H3).** Every bus event (`state-changed`, `button`, `inference`, `custom`) is *best-effort mirrored*: `publish_event` tries to write it to `event_log` first so the delivered event carries its `row-id`, but a write that errors, panics, or exceeds `MirrorPolicy::write_deadline` (2 s) does not refuse the publish. The event is delivered with no row id (WIT `row-id: none`, Connect `row_id = 0`, JSON tail frame without `id`) and the mirror enters **degraded mode**: later publishes skip the disk until `probe_interval` (5 s) has passed, then the next publish probes. No write starts while an earlier one is still running (timed out, or orphaned because its publish future was dropped by a trap or watchdog kill and released the gate): the publish goes out unrecorded instead, so a hung disk can't pile up blocking threads and rows can't commit out of order. The blocking write settles health itself, so a cancelled publish still counts. Events skipped while a recovery write runs are kept for the next marker. Records that must be durable before the action proceeds (the C3 `audit_event` ledger) are a separate, fail-closed path; no bus event is in that class today. The C2d rate limit and the H9 projection pre-check still run before any disk work. `state::event_log::mirror`.
- **Gaps are explicit (H3).** When a probe succeeds it writes a **gap marker** row in the same transaction as the probing event: topic `host.event_log.gap`, `plugin_id = instance_id = "host"` (no plugin can publish under that origin, because manifest validation requires a dotted `plugin.id`), custom payload `{"unrecorded", "first_received_ms", "last_received_ms", "last_error"}`. Its row id sits between the last pre-outage row and the first post-recovery row, and it is fanned out live, with that row id, just before the probing event (or, if that publish was cancelled, before the next one). Marker bounds are the min / max receive times of the unrecorded events. Gap markers bypass subscription filters (bus) and device / instance / plugin / topic filters (history queries, via a second index scan merged by id); time and cursor bounds still apply. How consumers detect a gap: a **live** consumer that receives an event without a row id must not advance its cursor, because that event is not in history; it then receives the marker before any later event that carries a row id. A **history** consumer (`GET /api/v1/events`, MCP `events.history` / `events.subscribe` with `after_id`) sees the marker at its cursor position. Cursor semantics don't change: row ids stay strictly increasing and every id is a valid cursor. A write that timed out can still commit later, below every later row id, so history order still matches delivery order, but `unrecorded` is then an upper bound and a consumer that replays history may see that event twice. A recovery write that commits after its deadline keeps the outage open but still fans its marker out with the next publish. The outage counter lives in memory, so if the daemon stops while degraded, no marker is written; the ERROR log line is the only record.
- **Degraded mode is visible (H3).** Entering degraded mode logs ERROR (`event_log.mirror`), each failed probe logs WARN, and recovery logs WARN with the gap size. `GET /api/v1/readyz` carries `"event_log": "ok" | "degraded"` and stays 200 (control still works), and the anonymous Connect `HealthService.Check` carries the same value in `CheckResponse.event_log` with `status` still `"ok"` (the H2 device-state projection reports `device_state` the same way, see *Device state (H2)*); its database ping runs off the async workers with a 2 s bound and at most 4 pings outstanding, so a hung write can't stall the probe or fill the blocking pool. The authenticated MCP `oxidhome://status` resource carries `event_log` with `degraded`, `degraded_since_ms`, `unrecorded_pending`, `unrecorded_total`, `gap_markers_total`, `last_error` and `last_recovered_ms`.
- **Ordering guarantee (H5 + H3).** `publish_event` holds the bus's `publish_sequence` gate across mirror write, projection update and fan-out. Every subscriber therefore receives events in gate-acquisition order (minus its own C2e drops), and among delivered events that carry a row id the ids strictly increase in that order. Events without a row id keep their place in delivery order. The gate is global, so a slow disk still serializes publishers: while healthy each publish holds it for at most one write deadline, and while degraded publishes do no disk work under it.
- **History-to-live handoff (H4).** The Connect `TailEvents` stream (`TailEventsRequest.after_id`) and the JSON tail (`GET /api/v1/events/tail?after_id=N`) take a resume cursor; a cursor needs `events:read` on top of `events:tail`, and an accepted cursor is acknowledged by the `oxidhome-resume-after-id` response header (the resolved cursor). No header means no resume: the cursor expired (the stream's only message is `cursor_expired`) or the server predates H4 and ignored `after_id`. **Guarantee:** a stream opened with `after_id = N` delivers every `event_log` row with `id > N` exactly once, in increasing id order, then continues live; `0` starts at the oldest retained row. Events without a row id (H3 degraded mirror, host simulators) are delivered in their publish position and never move the cursor; gap markers are ordinary rows, so a marker still arrives before the recovery event. The one allowed duplicate: an event delivered live without an id whose timed-out write commits later is replayed from history with its id, just before the next row-id event (normally the recovery gap marker). **Mechanism** (`state::event_tail::EventTail`): `EventBus::subscribe_at_head` subscribes and snapshots the bus's fanned-out row-id watermark `W` under the `publish_sequence` gate (seeded at boot with the history head; the database is never read under the gate, and live-only opens skip the gate), so rows `<= W` reached subscribers before the subscription existed and every later fan-out is queued. The stream replays `(N, W]` from history in pages of 32, then drains the queue: ids `<= cursor` are skipped, `cursor + 1` is delivered, and a larger id makes the stream read the missing rows from history first (queue overflow, or a row committed without fan-out by a cancelled publish). Each queued message also carries the watermark at its fan-out (`rows_through`), so an event without a row id that follows dropped rows waits for them, and when the queue is empty and the bus watermark is above the cursor the stream replays rows dropped at the end of a burst without waiting for another publish. A row committed without any fan-out is delivered when the next row-id event arrives. Row ids are dense (`AUTOINCREMENT`, one serialized writer, failed inserts roll back their id) and retention deletes only an id prefix, so a replay range that comes back short proves rows were pruned. History reads run on the blocking pool, at most 8 at once, with a 10 s deadline, and the WebSocket keeps a running read across client frames; a failed read ends the stream (Connect `unavailable`, WebSocket close 1011). Without a cursor the stream is live-only, as before.
- **`cursor_expired` (H4).** A cursor is expired when it is above the history head (`sqlite_sequence`, e.g. after restoring an older backup) or the row right after it was deleted by retention, including rows pruned while a stream is still replaying. Retention (`EventLog::trim_older_than` and the periodic retention task) deletes only an id prefix: the rows below the first row received at or after the cutoff, or below the newest `OXIDHOME_EVENT_LOG_MAX_ROWS` rows (under a clock rollback an old-stamped row above it waits for the rows before it), so checking the row after the cursor is exact. The tails emit one `cursor_expired {after_id, oldest_id, head_id}` message (Connect `CursorExpired` body; JSON `{"cursor_expired": {…}}` followed by a normal close) and end instead of skipping rows. `GET /api/v1/events?after_id=` answers `410 Gone` with the same body, MCP `events.history` / `events.subscribe` return an `isError` result with it in `structuredContent`, and the `oxidhome://events` resource fails with JSON-RPC error `-32005` carrying it as `data`; those run the query and the cursor check in one `Db::read` closure, so both see one read snapshot (M6). To resync, the client reopens with `after_id = head_id` first (that recovers every retained row after the head; events without a row id, H3 degraded mode, published between the expiry and the reopen are not in history and can be lost), then rebuilds device state from the projection rather than from events: read the paginated snapshot (`GET /api/v1/devices/state`) and follow its pinned `revision` with `GET /api/v1/devices/state/changes`. Device state also changes without a bus event (`execute-command` `OkWithState`, registration), so replaying buffered `state-changed` events over a snapshot could overwrite a newer value; the revision cursor can't.
- **Lag recovery (H4).** The lag notice carries the cursor to resume from: Connect `Lagged.resume_after_id`, JSON `{"lagged": N, "resume_after_id": ID}` — the stream's resume cursor when the notice is emitted, i.e. the highest row id delivered so far (absent in live mode if none yet). A live-only stream stays lossy; the client reopens with `after_id = resume_after_id` to recover the dropped events that are in history. A cursor stream re-reads them from history itself, so its notice is informational; dropped events without a row id are lost in both modes (H3 marker accounting still covers the ones the mirror skipped).
- **Plugin history reads.** `host-events::read-events(after-id, limit)` lets a plugin replay recorded events, e.g. to resume `on-event` from the last `row-id` it handled after a restart or a lag. **Scope follows live delivery:** the call needs `capabilities.subscribes_events` (otherwise `permission-denied`, plus an audit `deny` row with `method = EVENTS`, `required_scope = subscribes_events`, written in the background as for H2's refused reads), and a row is visible when it matches one of the instance's *current* subscription filters (the bus's own `filter_matches`), so history never shows a plugin more than `on-event` would. H3 gap markers are always visible. Invisible rows are skipped silently: the cursor moves past them and nothing says why (row ids are visible to live subscribers anyway). `bytes-val` fields become the M7-style `json-val` marker with `required_scope: "reads_event_bytes"` unless the effective capabilities set `[capabilities] reads_event_bytes = true` (requested ∧ granted); unlike H2 there is no own-event exemption, because `event_log` doesn't record the publisher's installation. **Paging:** the result is `page {events, next-after-id, head-id}` or `cursor-expired {after-id, oldest-id, head-id}` with H4's semantics (`0` starts at the oldest retained row; a pruned or future cursor expires). A page holds at most `limit` events (0 → 64, max 256) and about 1 MiB (at least one event), and a call looks at no more than 1024 rows, so a sparse filter yields short or empty pages; `next-after-id` is the last row consumed (the head once the scan reaches it; a missing run of rows, left by pre-H4 time-based retention, ends the page so the next read reports `cursor-expired`), and the plugin is caught up when `next-after-id >= head-id`. **Mechanism:** `EventLog::scan_after_cursor` checks the cursor and steps one statement in one `Db::read` snapshot (M6 read pool), decoding a row only when the scan reaches it (a row that doesn't decode is logged and skipped, so it can't block every reader behind it); it runs on the blocking pool behind a 4-slot process-wide semaphore with a 10 s deadline (`unavailable` after it), since the wasm watchdog can't interrupt a parked host call. **Live order:** `on-event` delivers events from all of an instance's subscription queues in row-id order: each drain sorts by the bus watermark at fan-out and holds back a recorded event fanned out after the watermark it read before draining (with the rest of that queue behind it, so each queue stays FIFO), so a cursor never skips an older event that was still on its way to another queue. A drain takes at most what each queue held when it started. **SDK:** `oxidhome_sdk::host::events::{read_after, History, Cursor}`; a plugin subscribes first, replays history from the cursor it keeps in KV, and drops live duplicates with `Cursor::advance` (`examples/event-recorder`).

### Device state (H2)

- **The projection is durable.** `DeviceStateStore::open_persistent` (migration 19: `device_state`, one row per `(device_id, capability)`, plus a one-row `device_state_meta`) restores every slot at boot, before any plugin runs, so reads are correct before owners republish. Rows carry the fields (a lossless tagged encoding: floats by bit pattern, bytes as hex), revision, `received_ms` / `observed_ms`, source generation, owner instance, owner plugin and owner installation UUID. Supervisor generations continue from the highest restored one. [ADR-0009](docs/adr/0009-durable-device-state.md).
- **Writes are coalesced and off the publish path.** A mutation marks its key dirty under the store lock (no I/O); a flusher thread waits 250 ms after the first change, takes the dirty keys and their current values under one lock (the store's state at one revision) and writes them in one normal-priority transaction. The H3 bus gate covers only the in-memory update, so a slow or failed disk never delays or refuses a publish; a failed flush logs, keeps its keys queued and retries every 5 s. The dirty set is capped at 16384 keys, past which the next flush rewrites the table. Shutdown runs a final flush (5 s bound) after the supervisors stop, so their stale flips are persisted.
- **Flush health is visible.** While flushes fail the projection is *degraded*: `GET /api/v1/readyz` carries `"device_state": "degraded"` (otherwise `"ok"`) and stays 200, the anonymous Connect `HealthService.Check` carries the same value in `CheckResponse.device_state` with `status` still `"ok"`, and the authenticated MCP `oxidhome://status` resource carries `device_state` with `persistent`, `degraded`, `degraded_since_ms`, `last_error`, `last_flush_ms`, `failed_flushes_total` and `pending_keys`. Live state and control are unaffected; a crash while degraded loses the queued changes.
- **Freshness rule.** A restored value is the owner's last report, not a confirmation: every restored `fresh` entry is flipped to `stale` (with a new revision) at boot and stays `stale` until the owner republishes it (`register-device` initial state, a `state-changed` event, or a command's `ok-with-state`). Consumers that need a live reading filter on `quality = fresh`.
- **Revisions and cursors across a restart.** The epoch is persisted. The flushed revision `R` is a consistent snapshot point, but the previous process may have issued unflushed revisions above it (crash, failing disk), so the restored store continues from `R + 2^32` and records `(R, R + 2^32)` as a skipped range, written at `synchronous = FULL` before the store serves anything. A `/state/changes` cursor `<= R` stays valid across the restart (clean or not: the client never saw anything the restore lost); a cursor inside a skipped range gets `reset_required`. Every restored slot is renumbered above the base (fresh ones by the stale flip, stale ones keeping `received_ms`), so a surviving cursor is sent the whole restored projection once. Each boot flush claims the table with its process nonce; a flush from an older store is refused. Every flush also stores a consistency marker with the hole list: the table's row count and a checksum over the meta row (epoch, revision, watermark, ranges, writer, row count). A boot whose meta row or row count doesn't match (a revision inflated by damage, a lost or extra row) starts a new history: a new epoch, revisions continuing past the damaged history's, and the eviction watermark there, so every earlier cursor resets. A meta row written before the marker existed is accepted once. The newest 16 ranges are kept; older ones fold into the eviction watermark. 2^32 per boot keeps revisions below 2^53 for about two million restarts. The snapshot pagination cursor also carries a per-process nonce, so a cursor from an earlier process answers 409. A snapshot page looks at no more than 16384 entries and can end early, even empty, with a `next_cursor`; when the budget runs out inside a device, that device is left for the next page, except the page's first device, which is always scanned whole so paging makes progress. Snapshot and changes pages (REST and Connect) also have a byte budget of 2 MiB, measured as an upper bound on the encoded size (JSON string escaping, the REST byte-array encoding of `bytes-val`, field framing), half of Connect's default 4 MiB receive limit: a page stops before the device (snapshot) or entry (changes) that would cross it, always sends the first one, and sets `truncated` (REST) / `truncated` (Connect `ListDeviceStateResponse`, `ListDeviceStateChangesResponse`) when it holds fewer devices or entries than `limit` because of a budget. A changes client advances its cursor as usual and polls again. A device within the per-device caps (32 slots of 16 KiB) encodes to under 4 MiB even at the escaping worst case. Continuation pages leave out entries newer than the revision pinned on page one; the client gets those from `/state/changes`, so a slot written mid-resync and then lost in a crash never sits in its snapshot with nothing to retract it.
- **What is lost.** Changes after the last successful flush (normally under 250 ms; longer while the disk fails). Their cursors land in the skipped range and resync. A slot that can't be decoded at boot is dropped and the epoch rotates with every cursor expired; `oxidhome restore` does the same, since the restored database is an older history.
- **Connect parity.** `DevicesService.GetDeviceState`, `ListDeviceState` and `ListDeviceStateChanges` mirror the three REST endpoints (`devices:read`, M7 bytes withholding, the same cursor and caps; a bad cursor is `invalid_argument`, a cursor from another process or epoch `aborted`).
- **Plugin reads.** `host-state::get-state(device)` and `list-state(filter, cursor, limit)` (pages of up to 256 devices and about 1 MiB; one call looks at no more than 4096 entries, the first device of the page excepted, so a page can be short while `next-cursor` is set) read the projection. The list cursor is sealed with the process's cursor secret, so a scan that stops on a hidden device doesn't reveal its id; a cursor from an earlier process is `invalid-argument`. An instance always sees the entries it wrote as the same installation (a reinstall under the same instance id does not inherit its predecessor's entries). Script sandboxes (`<parent>~<local-id>`, ADR-0001) are distinct instances: a sandbox and its parent don't read each other's entries as their own; they share the installation's `reads_state` grants, so a grant naming the plugin's own id opens them to each other. Other entries need a `[[capabilities.reads_state]]` grant (`plugin` owner id or `*`, `capabilities`, `devices` defaulting to `*`, `bytes`); the effective grant is the requested and granted lists intersected by equality, at most 64 entries. Installs that predate the field have no grant. Without `bytes = true` on a matching grant every `bytes-val` becomes `{"withheld":"bytes","size_bytes":N,"required_scope":"reads_state.bytes"}`. `get-state` answers `not-found` both for an unknown device and for one with no entry the plugin may see, with the same message and no extra wait, so a plugin can't probe which device ids exist; the second case also writes an audit `deny` row in the background for the operator (`method = STATE`, `path = device.state/<instance>/<device>`, `required_scope = reads_state`, the invocation's call id; queued to one audit worker thread, at most 64 pending, past that the refusal is dropped and counted; shutdown waits up to 2 s, after the supervisors stop, for the queue to drain); `list-state` silently leaves invisible entries out. Allowed reads are traced, not audited. Secrets never reach the projection: it holds only device state the owners published.

### Invocation context (H6)

- **Authorization is per credential; attribution is per invocation.** `Actor` is what the bearer middleware resolves from a token (token id + scopes + 14.4 constraints + roles, deny list and sensitive grants). Each external entry point additionally mints a host-only `auth::InvocationContext`: a `call-<32 hex>` call id, a root `Principal` that models `subject`, `credential_id` and `transport` (`rest` / `connect` / `mcp-http` / `mcp-stdio` / `host`) separately instead of folding them into `Actor.id`, the root's resolved `Authority` (token id, scopes, constraints, roles, deny list, sensitive grants, owner flag; never serialized, not in `invocation_json`; empty for `host` roots), the executing instance, a deadline (`EXTERNAL_INVOCATION_DEADLINE`, 60 s), and the `call-service` delegation chain. REST and Connect mint one per authenticated request in their bearer middleware; MCP mints one per `tools/call` (and a transient one per resource read and prompt, used only to authorize).
- **The context crosses the plugin boundary, the plugin never sees it.** It rides `ControlCommand::Execute` / `ExecuteService` to the owning supervisor, which scopes it as a `tokio::task_local` while the wasm runs; the `plugin.execute_command` / `plugin.execute_service_command` spans record its `call_id` (persisted span paths are unchanged). Host imports on that task — today `call-service` — read it; nothing is exposed through WIT, so a plugin can neither read nor forge its root. Work the host starts itself (`init`, `tick`, `on-event`, `InstanceHandle::execute_command`) runs under a `host`-transport context rooted at the instance.
- **Deadlines are enforced at dequeue.** A supervisor refuses an `Execute` / `ExecuteService` whose deadline already passed instead of actuating a device for a caller that gave up; a device command refused this way is `timed_out` (H5), a service call is `unavailable` (it did not run).
- **Downstream audit rows carry the root.** `audit_event` gained `call_id` and `invocation_json` (migration 17). The entry point's row and every delegated `call-service` hop of an externally-rooted invocation share the call id; hop rows use `method = CALL`, `path = service.call/<plugin>/<instance>/<local-id>/<command>`, the root's `token_id` / `actor_kind`, and the context JSON (root, executing actor, chain). Allowed hops are two-phase and fail closed; grant refusals are `deny` rows with `required_scope = consumes_services`; other pre-dispatch refusals (same-instance, cycle, expired deadline, M2 schema, owner not running) write no row. Host-origin chains are traced, not audited, so ledger volume tracks external requests. `GET /api/v1/audit?call_id=…` returns one invocation's rows.
- **One decision point for external callers.** Every token-scope check on REST, Connect and MCP calls `auth::authorize(ctx, action, resource) -> Decision`. `Action` is a closed `kind.verb` enum (`device.list`, `device.read`, `device.command`, `event.subscribe`, `event.read`, `blob.read`, `instance.read` / `start` / `stop`, `plugin.read` / `install` / `uninstall` / `ui`, `dashboard.read` / `write`, `host.status` / `logs` / `audit`, plus `token.manage`, `policy.manage`, `service.call`, `state.read`, which no token scope or role grants; the owner alone holds `token.manage` and `policy.manage`). `Resource` is built by host code from the id the call addresses: `Host`, a `Collection(kind)` for lists and streams that release every item, a `PreCheck(kind)` made before the target is known when a per-target check or per-item filter always follows, or one device, plugin, instance set, blob or dashboard. `Decision` is `{allow, reason, obligations}`; `obligations` carries an audit level (`warn` for an allowed sensitive action, else `info`), a rate limit (set for a non-owner's sensitive action) and a confirmation field that nothing sets yet.
- **The evaluator is the scope model.** Each action maps to the one scope that always gated it (`device.command` → `devices:command`, `event.subscribe` → `events:tail`, `host.status` → `status:read`, …); a token holds it by literal match or `*`. A 14.4 constraint narrows the scope only when the resource names its target: `device.send_command` / `devices` on `device.command` for a device, and `plugins.show` / `start` / `stop` / `uninstall` / `install` / `plugins` on `plugin.read` / `instance.start` / `instance.stop` / `plugin.uninstall` / `plugin.install` for a plugin. Handlers that learn their target from the request body (MCP tools, Connect) authorize the action on the pre-check first, then again on the target; the MCP `plugins.install` tool authorizes the manifest-derived id inside `install_gated`, before any side effect (REST and Connect install check `plugin.install` on `Host`, since they refuse `plugins.*` constraints at verify time). Plugin UI tickets (`/ui/frame`) are still checked against their signed plugin id and installation, not through `authorize`. The MCP `oxidhome://plugins/{id}` read is checked on the plugin collection, so `plugins.show` does not apply to it. Plugin principals are still authorized by their manifest grants at their own call sites (`consumes_services`, `reads_state`, `subscribes_events`). A table-driven test runs every former call site's check and `authorize` side by side and asserts the same allow or deny and the same audit label; it verifies the evaluator, and transport tests cover which action and resource each route passes and the prompt check order.
- **Sensitive categories need an explicit grant (H6 slice 2).** `authorize` refuses `device.command` on a `lock`, `opener` or `alarm` device and `blob.read` of camera bytes unless the token's policy, or one of its roles, names the category: `{"scopes": [...], "sensitive": ["lock", {"category": "camera", "devices": ["dev-ab12*"]}]}`. No scope reaches them, `*` and `devices:command` / `blobs:read` included. A grant only adds the category on top of what the scopes and 14.4 constraints already allow, and a device-narrowed grant covers only those ids (never a blob addressed by instance and name). Camera *control* is not sensitive; camera bytes are: a camera device's `bytes-val` in state, events and command results, and every blob or `bytes-val` of an instance that has registered a camera (bytes carry no provenance of their own). The deny label is `sensitive:<category>`. The **owner token** (the one minted at first-run bootstrap or by `recover-admin-token`; `auth_token.owner`, set only by those paths and backfilled by migration 21 from their audit rows; when retention has pruned them, startup warns that no owner exists and points at `recover-admin-token`, which revokes the previous owner; a partial unique index keeps one live owner) holds every category and alone holds `policy.manage` and `token.manage`. Other tokens are edited offline with `oxidhome token grant-sensitive <id> <category> [--device <dev-id>]...` / `revoke-sensitive`; the daemon logs a `warn` at startup naming every live non-owner token whose `*`, `devices:command` or `blobs:read` scope no longer reaches a category it used to (a category one of its roles grants counts as reached). `mcp-stdio` runs as a non-owner wildcard actor and reaches a sensitive category only with `--allow-sensitive <category>`.
- **Roles and the deny list (H6 slice 3).** There are no built-in roles: the owner defines them. A role is a row of `auth_role` (migration 23): an id (`role-<16 hex>`), a unique name (1 to 32 of `a-z0-9-_`, starting with a letter, never `owner`) and a definition `{"grants": [{"actions": [...], "category": [...], "devices": [...]}], "sensitive": [...], "deny": [...]}` (`auth::RoleDef`). Grants name only actions a scope can grant (`*` means all of those), so a role never reaches `token.manage`, `policy.manage`, `service.call` or `state.read`, and a grant narrowed to categories or device ids names only `device.list`, `device.read` and `device.command` (a narrowed `*` means those); `sensitive` lists the sensitive categories the role grants on every device. The owner manages roles with `oxidhome role list|create|update|delete [--force]` (offline), `/api/v1/roles` (`GET`, `POST`, `PUT /{name}`, `DELETE /{name}?force=true`) or Connect `RolesService`, all `policy.manage`; each write leaves an `audit_event` row with path `<surface>.auth.role.<create|update|delete|delete-forced>:<name>`, and a host holds at most 64 roles. A token policy names roles by id next to its scopes and its own deny list: `{"scopes": [], "roles": ["role-…"], "deny": [{"actions": ["device.command"], "category": ["alarm"], "devices": ["dev-ab12*"]}], "sensitive": [...]}`. The API layer resolves the ids against `auth_role` on every request (`actor_from_record`), so an edit applies to every token holding the role from its next request on (a stream keeps the roles it started with); a role that live tokens hold is deleted only when forced (a mint checks its roles in the same transaction as the insert), and a reference to a deleted role grants nothing; a role whose definition doesn't parse, or a failed read of the roles, makes the token deny-all for that request. Roles are expanded only inside `authorize`; there is no second check path. A role grant narrowed to categories or device ids matches a device by its display category (only while the device is registered; an offline device's category is unknown) and id, and covers the device pre-check, never a collection: list endpoints (`GET /api/v1/devices`, Connect `ListDevices`, MCP `oxidhome://devices`) pre-check and then authorize each row, while whole-fleet reads (`/devices/state`, `/devices/state/changes`, event history and tails) refuse such a token. A deny, the token's own or a role's, is checked first and beats every grant, the wildcard, sensitive grants and the owner flag (label `deny`); a category deny matches a device whose display category or sensitive set names it (and every device not registered right now, whose display category is unknown; a light owned by a camera instance keeps `light`, its bytes adding `camera`), any deny with a selector matches a whole device, event or blob collection, a device-narrowed deny matches every blob (blobs name no device), and no deny with a selector matches a pre-check (an unconditional one refuses it outright). `service.call` is never checked for tokens (a delegated hop is governed by the calling plugin's `consumes_services` grant), so a mint or role refuses a deny that names it except through `*`. The sensitive rule and 14.4 constraints apply on top of a role exactly as on top of a scope, a role's `sensitive` categories counting as grants. A denied role-holding token gets `no-permit` when a role grants the action elsewhere, else the missing scope. Tokens are minted by role name with `oxidhome token create` (offline) or by the owner over `POST /api/v1/tokens` / Connect `TokensService.CreateToken`, which refuse an unknown name and `owner`; `GET /api/v1/tokens`, Connect `ListTokens`, MCP `tokens.list` and `oxidhome token list` list them without secrets, a deleted role showing as `<id> (deleted)`. MCP has no mint or role-write tool: its responses are redacted (M7), and a secret must not reach an LLM's context. A mint is a plain token (never the owner) and writes a two-phase `audit_event` row whose `token_id` is the new token and `path` is `<surface>.auth.mint:<role names>`. The `admin` label stays reserved for the owner, since `recover-admin-token` revokes tokens by that label. Scope-only tokens are unchanged; the parity tests check sample roles against an independent oracle and unnarrowed ones against their equivalent scope lists.
- **Allowed sensitive actions carry obligations.** The decision's `obligations` name the sensitive categories, an audit level of `warn`, and (except for the owner) a per-principal, per-category rate limit: 10 commands per 10 minutes for `lock` / `opener` / `alarm`, 120 camera releases per 10 minutes. `auth::sensitive::SensitiveGuard` meets them before the action: it takes a token from every category's bucket (all or nothing; `429` + `Retry-After` on REST, `resource_exhausted` on Connect, MCP `-32006`), then writes a completed `method = AUTHZ` audit row with `level = warn`, `path = authz.<action>:<target>`, `required_scope = sensitive:<categories>` (or `owner:<categories>`) and the request's `call_id`; a command doesn't run if the row can't be written. For a device command the two are split: the surface reserves the charge at admission (so the `429` is immediate) and the charge rides with the queued command (`SensitiveCharge`); the supervisor writes the `warn` row only once the command has won `queued → started` and passed re-authorization, just before the plugin is entered. A command withdrawn, timed out or refused before that is refunded when the supervisor drops it and leaves no `warn` row (its deny or timeout rows are unchanged). Reads release camera bytes through one `api::bytes::BytesGate` per response or stream: the first camera value it would release meets the obligations (the `warn` row is written off the request path, best-effort), and a principal over its camera allowance gets the withheld marker for the rest of that response or stream. `GET /api/v1/audit?level=warn` lists the rows. Confirmation is not implemented.
- **Denies keep their audit shape.** A deny is a bare `403` / `permission_denied` / MCP `-32001`. On REST, Connect, MCP tools and MCP resource reads the reason's audit label goes to the row's `required_scope`: the missing scope, `constraint:<key>:<field>` for a constraint, `no-permit` for an action no scope grants. MCP `prompts/get` writes no audit row; its `-32001` message names the missing scope. REST and Connect accept only the `device.send_command` constraint key (`DEVICE_COMMAND_ENFORCED`) and refuse every other one at verify time, as before.

### Command outcomes (H5)

- **Every device command gets a host-minted id and an explicit outcome.** `InstanceHandle::execute_command_in` mints `cmd-<32 hex>` (the same generator as H6 call ids) into `command.id`, whatever the caller sent, and returns a `CommandReport { command_id, outcome }`. The outcome is one of `accepted`, `completed`, `rejected`, `timed_out`, `outcome_unknown` ([ADR-0003](docs/adr/0003-explicit-command-outcomes.md) has the full transition table). `rejected` and `timed_out` mean the command did not act and are safe to retry; after `outcome_unknown` a caller reads the device state before retrying.
- **Queued vs started is one compare-and-swap.** Each `Execute` carries a `DispatchTicket`. The supervisor moves it `queued → started` just before entering the plugin; the caller moves it `queued → abandoned` when its deadline passes or its future is dropped. Only one wins, so a `timed_out` command never runs, and a command the plugin entered can only end in the plugin's own reply or `outcome_unknown` (trap, watchdog kill, deadline mid-call).
- **The plugin's reply says what it did.** WIT `command-result` gained `unknown(string)` (the plugin can't tell whether the device acted) and `accepted` (the plugin took the command and finishes it later); `err` now means "refused without acting". An `ok-with-state` the projection refuses (caps, sensor units) becomes `outcome_unknown`, since the plugin reported success.
- **`accepted` completes through `complete-command`.** The host records an accepted command in the engine's `PendingCommands` table (bounded: 64 per instance, 1024 total; an overflow answers `outcome_unknown`). The owning instance calls `host-devices::complete-command(id, reply)` once; an `ok-with-state` reply is projected exactly like a synchronous one. An entry not completed within 5 minutes, or still pending when its instance restarts or stops, expires as `outcome_unknown`. There is no lookup API yet: the final outcome lands in the audit ledger as an append-only `COMMAND` row (`path = device.command/<device>`) with the request's `call_id` and `command_id`. Late results (a reply after the caller timed out) and queued commands whose caller disconnected are recorded the same way, exactly once whichever of the supervisor's send and the caller's drop comes first (the caller's reply guard records a reply sent but never read, the supervisor one it couldn't send), including commands refused during a restart backoff or still queued when the supervisor goes terminal (`rejected`, or `timed_out` when the caller had already gone or its deadline passed; a terminal supervisor refuses its queue instead of dropping it). An expiry row's `domain_error` says why: `expired`, `instance_restarted`, `instance_stopped` or `daemon_restart`.
- **Pending commands survive a restart as `outcome_unknown`.** Externally-rooted pending entries are written behind to `pending_command` (migration 20: command and call ids, owner instance, device, capability, created and expiry wall-clock times, and the request's `token_id` / `actor_kind` / invocation JSON). One bounded writer thread, the command journal, applies persists and resolution rows in queue order at normal priority through the M6 writer, up to 256 jobs per transaction; a resolution row and the delete of its persisted entry commit together, so a command is either still in the table or has its final row. A command completed before its persist was written can't resurrect: the delete is ordered after the insert. At boot, before any plugin runs, every surviving row becomes a `COMMAND` row with `outcome_unknown` and `domain_error = daemon_restart` (or `expired` if its expiry had passed); a failed reconciliation stops the boot, and a late resolution whose row was already reconciled writes no second row. The queue holds 4096 jobs: past that a persist is skipped (memory-only tracking) and a resolution of a never-persisted command is dropped and counted, while a persisted command's resolution is always queued. Shutdown drains the journal for up to 5 s after the supervisors stop. The command path only pushes to the journal queue (a sensitive command's `warn` row is the one durable write before dispatch), so pending-command persistence does no disk I/O on it, so a crash in the few milliseconds before a persist is flushed leaves that `accepted` request without a final row.
- **Service calls get the same ticket.** `ExecuteService` carries a `DispatchTicket` too. A `call-service` whose wait ends while the call is still queued answers `unavailable` ("it did not run", safe to retry); once the callee started, a missed deadline or a lost supervisor answers `ok(unknown(..))`, and the H6 hop row is finalized `allow` with no execution outcome; the result, if the callee still produces one, is recorded as a `CALL_RESULT` row with the hop's `path` and `call_id`. Hop finalizes are queued on the command journal, so shutdown drains them and a runtime teardown can't cancel them. Service calls stay synchronous: a callee's `accepted` becomes `unknown`.
- **Wire mapping.** REST returns `{command_id, outcome, retry_safe, state?, error?, message?}` with `completed` → 200, `accepted` → 202, `rejected` → 422, `timed_out` → 504, `outcome_unknown` → 502 (a gateway-style answer that carries the command id, never a bare 500). Connect bounds dispatch by the earlier of the invocation deadline and the client's `Connect-Timeout-Ms` / `grpc-timeout`, keeps an OK status and adds `command_id` + `command_outcome` with `accepted` / `timed_out` / `outcome_unknown` oneof arms. MCP `device.send_command` returns the same JSON as REST, with `isError` set for `rejected`, `timed_out` and `outcome_unknown`. The audit `decision` stays `allow` for every dispatched command whatever the outcome (F4).

### Audit and access

- **API requests hit a dedicated audit ledger.** `audit_event` is separate from the diagnostic `log_event` stream so a burst of debug logs can't evict audit rows. Writes are two-phase: `record_intent` before the handler runs, `finalize` after — a client disconnect mid-handler leaves the pending row behind as evidence of the attempted action. **C3.**
- **Authorization outcome and execution outcome are separate audit fields.** `decision` carries the auth outcome (`allow` / `deny` / `error` / `pending`), `status` carries the wire HTTP status, `execution_outcome` + `domain_error` carry the plugin's `CommandResult::Err` kind, and `command_id` + `command_outcome` (migration 18) the H5 command id and outcome. A plugin returning an error on an authorized request no longer shows up in `WHERE decision = 'deny'` searches. **C3 review F4.**
- **Tokens are hashed at rest.** 256-bit CSPRNG bearer tokens, SHA-256 at rest — plain SHA is correct for a uniformly-random 256-bit secret; a slow KDF only pays off against low-entropy passwords. `revoked_ms` is a tombstone; rows aren't deleted so audit lineage stays intact. **12-API tokens.**
- **Admin bootstrap is crash-safe and recoverable offline.** The first-run admin secret is fsynced to `<state_dir>/admin-token.pending-<id>` before its row commits, then renamed to `admin-token`; a failed delivery rolls the row back, and startup reconciliation promotes an interrupted delivery and removes `admin-token` once its token has been used. A lost admin secret is recovered with `oxidhome recover-admin-token [--revoke-all]`, which only runs under the exclusive state-dir lock (daemon stopped) and is never exposed over the network. Bootstrap, recovery, revocations and file removals land in `audit_event` (`method = LOCAL`, `path = host.auth.*` / `cli.auth.*`). **M4.**

### Network access (Phase 8)

Streaming-world instances reach the network only as far as their **effective** `[capabilities] network` rules allow. Only `streaming-plugin` and `streaming-ai-plugin` manifests may declare `network` rules; on any other world they are a validation error. Grants narrow by containment: the effective rules are the granted rules some requested rule covers plus the requested rules some granted rule covers, so an operator can grant one camera out of a requested `192.168.0.0/16`, a narrower port range or a `*.suffix` subdomain, but a rule only partly inside the request grants nothing. A rule covers another when its proto is the same or `any`, its ports include the other's, and its host covers the other's under the rules below (a `0.0.0.0/0` rule doesn't cover `10.0.0.5`, a `*.arpa` rule doesn't cover the local-only `*.home.arpa`). One per-instance policy decides every socket connect, UDP send, received datagram, bind, name lookup and HTTP request (`runtime::network`):

- **Decided on the resolved IP.** Addresses are canonicalized (IPv4-mapped IPv6 → IPv4) and classified as in the media policy. Unspecified, broadcast, multicast, documentation and reserved addresses are always refused — so broadcast / multicast discovery isn't possible yet.
- **IP and CIDR rules** cover the addresses they contain. A literal grants its own address whatever its class; a CIDR grants loopback, link-local or private addresses only when the whole range lies inside that class's blocks, so `0.0.0.0/0` covers public space only. A CIDR inside `::ffff:0:0/96` is matched as the IPv4 range it maps.
- **Name rules** (`host.example.com`, `*.example.com`) cover the *public* addresses the host itself resolved a matching name to. A name rule under a local-only suffix (`.local`, `.lan`, `.home.arpa`, `.internal`, e.g. `tcp://mqtt.lan:1883` or `https://*.home.arpa`) also covers the *private* addresses its names resolve to; no name rule ever covers loopback or link-local addresses (`metadata.google.internal` resolves to `169.254.169.254`). `wasi:sockets/ip-name-lookup` is host-implemented: names no rule mentions aren't looked up, names are resolved as absolute names (no resolver search list), and answers no rule allows are dropped before the plugin sees them, so DNS rebinding can't reach loopback, and can't reach the LAN through a public name. Each resolved address is remembered per rule for 10 minutes (at most 1024 addresses per instance); resolving one name never extends another name's grant. Only the well-known NAT64 prefix is decoded; a network-specific NAT64 prefix is treated as ordinary IPv6.
- **Binds** only to the unspecified address (any port); `listen` is refused.
- **`wasi:http`** is sent by the host: it resolves and checks the request's host (`tcp` / `any` rules for `http://`, `https` / `any` for `https://`) and connects to exactly the address it checked. Redirects are never followed, so every hop the plugin follows is a new, checked request. `https://` requests are refused until TLS ships.
- **Ceilings** per instance: 64 live sockets, 4 concurrent lookups (5 s timeout), 16 concurrent HTTP requests, 4096 resource-table entries (sockets, lookups and `wasi:http` resources hold host memory outside the guest's memory ceiling), outgoing-body writes of at most 16 KiB with at most two buffered per body, request method / authority / path of at most 64 B / 512 B / 8 KiB, header maps of at most 16 KiB with names of at most 256 B, response heads of at most 64 KiB, and at most 128 network rules per manifest; name lookups are also capped host-wide (32 in flight). URLs with userinfo, or with anything but `host[:port]` in the authority, and `CONNECT` requests are refused. One connect deadline covers an HTTP request's lookup, every allowed address it tries (each with an equal share of the time left) and the handshake. A lookup hands the plugin at most 32 addresses. A streaming manifest whose component doesn't export `oxidhome:plugin/streaming` is refused at load.
- **Readiness wakeups.** Between calls, the supervisor of a streaming instance whose manifest sets `tick_interval_ms` also waits on the read side of the sockets the guest holds open: TCP input streams (a connected socket's, told apart from other input streams by being the socket's child in the resource table) and UDP incoming-datagram streams (`runtime::io_wakeup`). When one is readable it runs `tick` early, with no WIT change: readiness is only checked while no call runs, so a burst wakes the plugin once, and an early tick starts no sooner than 100 ms after the previous tick returned, measured on the engine clock. It is an ordinary `tick` (watchdog, stop first, events drained after). A socket the plugin leaves readable wakes it again after each gap. Datagrams the policy drops on receive never make the stream readable. `wasi:http` responses and bodies are not watched. Without a tick cadence there are no wakeups.
- **Refusals are audited** in `audit_event` (`method = NET`, `decision = deny`, `required_scope = network`, `path = net.<op>/<instance>/<target>`, the reason in `domain_error`, and the call that caused it — lookups and HTTP requests carry the invocation onto the tasks they spawn), rate-limited per instance (burst 16, then 1/s). Dropped datagrams are not audited.

### Data classification and redaction (M7)

- **Secrets are a config type, not a convention.** A manifest field declared `type = "secret"` (optional `required = false`) is string-valued and may not carry a `default` — the manifest ships in the package and is served by the schema endpoint. The value arrives as a per-instance override and resolves to `ConfigValue::Secret(SecretString)`, whose `Debug` and `Serialize` both emit `"***"`. Only the owning plugin's `host-config` calls see the plaintext. Merge errors for a secret name the type, never the value.
- **Read APIs return a masked config view.** `InstanceHandle::config_view` (`redact::masked_config_view`, computed once on the first successful load) is the only instance-config shape the host serves: REST `GET /api/v1/instances` (`config`), Connect `ListInstances` (`config_json`) and MCP `oxidhome://plugins/{id}` / `plugins.show` (`instances[].config`). A secret field renders as `{"secret": true, "set": <bool>, "value": "***" | null}`. The daemon's own configuration is a separate read: MCP `oxidhome://config` and REST `GET /api/v1/config` (both `status:read`) return the effective settings with their source (`default` / `env` / `flag`) and the build, SDK and WIT versions; they carry paths and limits, never secrets, and still go through `redact::redact_json`.
- **Redaction happens at capture, in one module.** `redact::is_sensitive_key` is a conservative key-name denylist: after lowercasing and dropping non-alphanumerics, a key is sensitive if it contains `password` / `passwd` / `passphrase` / `secret` / `apikey` / `privatekey` / `authorization`, ends with `token` / `accesskey` / `credentials` / `cookie`, or is exactly `pwd` / `pin` / `auth` / `credential` (`token_id`, `credential_id`, `max_tokens` stay readable). `redact::scrub_text` masks `key=value` / `key: value` pairs with such keys (spaces or tabs around the separator, never across a line break; a `{…}` / `[…]` value is masked whole, to the end of the text if it was cut short), `Bearer <credential>` and `oxh_` API tokens in free text. They are applied (1) by the `SQLite` log layer to every event's message, structured fields and attribution columns before the row is queued (a value that is a whole JSON document is redacted structurally via `redact::redact_text`), so REST, Connect, MCP and the CLI all read redacted logs; (2) by `AuditLog` to the `path`, `domain_error` and `invocation_json` columns on every write (`invocation_json` structurally, so it stays valid JSON; the ledger records who did what, never command arguments or config values — a future column that does must go through `redact::redact_json`); (3) to every MCP resource body and tool result (`redact_json` masks values under sensitive keys, the `{key, value}` and `[name, value]` wire shapes, and scrubs strings); and (4) to a plugin's own `logging::log` lines, which have the plaintext of its declared secrets (≥ 4 bytes) replaced before they reach `tracing`; and (5) to a plugin's WASI stdout / stderr, which are host-owned rather than inherited from the daemon (`runtime::plugin_stdio`): output is line-buffered, each line has the instance's declared secrets and then the generic rules applied, is capped at 4 KiB, spends a token from the instance's `logging::log` rate bucket, and is emitted as a `tracing` event with target `plugin.stdout` (INFO) or `plugin.stderr` (WARN) carrying `instance_id` and `plugin_id`. Plugin stdin is empty. Redaction is defence in depth, not a guarantee: a plugin that encodes a credential in an unrecognised shape is not caught.
- **Raw bytes need `blobs:read`; camera bytes also need the `camera` grant.** Camera snapshots, audio and inference frames ride the read surfaces as `bytes-val`. Camera bytes are a sensitive category (see Invocation context): without an explicit `camera` grant they are withheld like below, whatever the scopes. Without `blobs:read` (the wildcard admin token includes it), device state (`GET /api/v1/devices/{id}/state`, `/devices/state`, `/devices/state/changes`), event history and tails (REST, Connect, MCP `oxidhome://events`, `events.history`, `events.subscribe`) and command results (REST, Connect, MCP `device.send_command`) replace each `bytes-val` with a `json-val` marker `{"withheld":"bytes","size_bytes":N,"required_scope":"blobs:read"}`. The blob store itself (`oxidhome://blobs/...`) already required `blobs:read`. **Migration:** a narrow token that needs those bytes adds `blobs:read` to its scope list. Camera bytes additionally need an explicit `camera` grant (`oxidhome token grant-sensitive <id> camera`); only the owner token has it without one, so a non-owner wildcard token loses them on upgrade.
- **Not yet covered:** encryption at rest and key management (secret overrides are held in memory for the instance's lifetime and are not persisted by the host today), backup / support-bundle encryption and sanitization (backups are unencrypted, see M3), and payload classification of events beyond the key-name redaction above.

### Path safety

- **Uninstall works on the recorded path, not a recomputed one.** `install` validates `plugin_id` shape before it enters the registry; `uninstall` deletes only the path the registry observed, with a `starts_with(plugins_root)` containment re-check before any `remove_dir_all`. A registry-corruption divergence refuses rather than escapes the plugins root.
- **Blob paths never escape `blobs_root`.** `check_instance_id` + `check_installation_uuid` refuse unsafe segments; `ensure_contained` re-verifies the resolved path lives under the root. Both checks fire at every blob-store entry point. **H1.**
- **Installed reads apply `O_NOFOLLOW` on the final component + hash the same buffers the loader compiles.** `read_installed_bytes` opens the target file with `O_NOFOLLOW` so a symlink swap of the leaf is refused, and the C5 digest verification hashes the same in-memory buffers the loader will compile from, closing the TOCTOU window a file-path re-read would reopen. **The stronger claim — full fd-relative traversal with beneath-resolution on every intermediate path component — is NOT yet in force**: intermediate directory components go through ordinary path resolution, and the runtime loader (`PluginInstance::load_with_overrides`) uses `tokio::fs::read` directly. Closing that gap on Linux via `openat2(RESOLVE_BENEATH)` is tracked as a follow-up (H12 review P1 F2). **C5 review round-4 (leaf O_NOFOLLOW) + open work.**

Design notes that don't yet correspond to a shipped invariant (Phase 6+ items in flight: `Engine::start_installed_instance` grant-scope refresh on manifest edit, `Engine::start_dev_instance` audit-log attribution, service dispatcher call-stack chain guarantees) live in the per-phase task-list rather than here — they promote up as they ship.

## North-star principles

These are the architectural tiebreakers:

1. **Security over convenience.** A capability-gated, sandboxed plugin model is the whole point. Don't add escape hatches that defeat the model. When you need an escape hatch (native bridges), make it explicit and visible.

2. **Honest about WASM's limits.** WASM is great for control-plane work and bad for codec-rate data. Design with that grain, not against it.

3. **Capabilities, not types.** Don't enumerate device archetypes. Compose capabilities. Make extension a first-class concept.

4. **The WIT is the product.** Other things change; the WIT is the contract plugin authors depend on. Iterate hard before 1.0; iterate carefully after.

5. **Fail clearly, not silently.** A misconfigured AI model running on CPU when the user expected GPU is a worse outcome than an upfront error. Visibility beats false positives.

6. **Native code is the exception.** The default story is "install a `.wasm` component and trust the sandbox." When that's not enough (vendor SDKs, hardware acceleration), it's a marked exception, not a parallel architecture.
